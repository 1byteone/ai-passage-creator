# AI Passage Creator 前端页面全面优化总计划

> 日期：2026-07-25
> 适用范围：`frontend/` 全站页面与设计系统
> 目标：基于当前仓库现状与权威前端设计规范，制定一份覆盖页面结构、视觉系统、交互体验、性能、可访问性、响应式和交付流程的前端页面优化开发计划。

---

## 1. 结论先行

这不是一个单页落地页优化任务，而是一个混合型产品的前端系统优化任务。当前仓库至少包含 4 类需要分别治理的页面形态：

1. 获客/入口页：`HomePage.vue`
2. 工作流页：`ArticleCreatePage.vue`、`SkillExecutePage.vue`
3. 结果与内容页：`ArticleDetailPage.vue`、Skill 结果组件
4. 数据与后台页：`StatisticsPage.vue`、`UserManagePage.vue`

因此推荐采用一套统一的 `Precision System` 设计方向，再针对不同页面角色做轻微偏置，而不是把所有页面都拉成同一种“营销页”或“卡片页”。

默认优化主线：

1. 先梳理信息架构和任务流，再调整视觉
2. 先统一设计 token 和核心组件，再扩展页面
3. 先修首屏理解、核心操作、状态反馈，再做高级动效
4. 先补可访问性、响应式和性能底线，再谈“高级感”

## 2. 当前仓库现状判断

### 2.1 页面形态判断

基于当前代码，产品已经形成以下页面分层：

| 页面 | 文件 | 当前角色 | 优化重点 |
| --- | --- | --- | --- |
| 首页 | `frontend/src/pages/HomePage.vue` | 获客 + 入口分发 | 首屏价值、真实证据、CTA 聚焦、模板感降低 |
| 技能中心 | `frontend/src/pages/skill/SkillCenterPage.vue` | 工具目录页 | 信息密度、分类、结果预期、空态与错误态 |
| 创作页 | `frontend/src/pages/article/ArticleCreatePage.vue` | 多阶段工作流 | 结构拆分、状态管理、移动端策略、信息噪音控制 |
| 统计页 | `frontend/src/pages/admin/StatisticsPage.vue` | 后台分析页 | 数据层级、图表可读性、辅助信息、图表无障碍 |

### 2.2 已观察到的设计与体验信号

1. 首页使用了明显的 Hero + 功能卡片组合，转化逻辑清楚，但仍带有较强模板化痕迹。
2. 当前设计 token 基本围绕单一绿色主题展开，品牌一致性不错，但容易造成整站色彩层次不够丰富。
3. 创作页采用三栏布局，信息量充足，但在 `992px` 以下直接隐藏左右侧栏，意味着移动端体验不是“重排”，而是“删减”。
4. Skill 相关页面已经开始补齐 `focus-visible` 和 `aria-live`，说明局部已具备较好的可访问性意识，但尚未形成全站一致标准。
5. 全局已经加入 `prefers-reduced-motion` 基础处理，但页面级动效、滚动和过渡还没有形成统一预算。
6. 创作页仍存在可见 emoji 与情绪化日志输出，不符合专业工具页的一致性标准。

## 3. 研究基线与外部标准

本计划优先参考以下权威与高可信来源，访问日期均为 2026-07-25：

1. [web.dev Core Web Vitals](https://web.dev/articles/vitals)
2. [web.dev Cumulative Layout Shift](https://web.dev/articles/cls)
3. [W3C WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/)
4. [MDN Responsive Images](https://developer.mozilla.org/en-US/docs/Web/HTML/Responsive_images)
5. [MDN CSS Container Queries](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_container_queries)
6. [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
7. [MDN ARIA live regions](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/ARIA_Live_Regions)
8. [Material Design 3](https://m3.material.io/)
9. [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/)
10. [GOV.UK Design System](https://design-system.service.gov.uk/)

### 3.1 研究结论摘要

1. 性能底线要围绕 Core Web Vitals 组织，尤其是 LCP、CLS 和交互响应。
2. 可访问性不应只停留在“颜色够不够深”，还要覆盖焦点、键盘、实时反馈、错误恢复和目标尺寸。
3. 响应式设计不能只靠 viewport 缩放，要重排内容层级、操作路径和密度。
4. 表单和工作流页必须把“错误怎么修复”设计清楚，而不只是提示“失败了”。
5. 后台页和工具页的高级感来自信息组织与状态清晰，不来自更大的阴影、渐变和装饰卡片。

## 4. 体验目标与完成定义

### 4.1 体验目标

本轮优化要同时实现以下 6 个目标：

1. 让新用户在首屏 5 秒内理解产品是什么、能做什么、下一步做什么
2. 让创作工作流在桌面与移动端都保持连续可理解，而不是局部消失
3. 让页面视觉系统从“单页风格”升级为“全站系统”
4. 让核心页面具备统一的状态覆盖：`hover / focus-visible / pressed / disabled / loading / empty / error / success`
5. 让高频页面达到稳定、清晰、可访问、可扩展的前端质量底线
6. 让后续新增 Skill、工作流和数据页能在同一规则下继续生长

### 4.2 完成定义

前端页面优化完成，至少需要满足：

1. 首页、创作页、技能页、详情页、统计页完成结构与视觉统一治理
2. 全站建立最小 design token 体系，并在核心组件中落地
3. 关键路径页面通过 375 / 768 / 1440 三档断点验收
4. 关键交互通过键盘、焦点可见、错误提示与 reduced-motion 验收
5. 关键页面补齐性能治理项并定义可量化指标
6. 产出文档化规范，后续迭代可复用

## 5. 推荐的设计方向

### 5.1 总体方向

推荐采用 `Precision System` 作为主导方向：

- 适合 AI 工具、内容工作流、后台与业务页面混合型产品
- 适合 Vue + Ant Design Vue 当前栈
- 便于从现有绿色主题平滑演进
- 有利于长期组件化和多页面一致性

### 5.2 各页面角色的偏置

| 页面类型 | 主方向 | 偏置策略 |
| --- | --- | --- |
| 首页 | Precision System | 增加少量内容证明与首屏聚焦，不做重营销化 |
| 创作页 | Precision System | 强调流程连续性、辅助信息分层、操作专注度 |
| 技能页 | Precision System | 更紧凑的信息组织和更强的结果预期表达 |
| 后台页 | Precision System | 数据优先、视觉克制、图表与指标的关系清晰 |

## 6. 核心问题清单

### 6.1 信息架构问题

1. 首页首屏能发起操作，但真实“证据区”较弱，容易停留在能力宣称。
2. 创作页承载过多辅助信息，左右侧栏与主内容竞争注意力。
3. 不同页面的标题、副标题、区块标题、提示文案语气不完全统一。
4. 高优先级动作和低优先级信息有时混排在同一视觉层。

### 6.2 视觉系统问题

1. 色彩系统以单一绿色系为核心，缺少足够稳定的中性色层与辅助角色。
2. 阴影、渐变、圆角虽已有统一倾向，但在不同页面的节奏感不完全一致。
3. 卡片使用较多，部分区块仍可进一步去卡片化、减少模板感。

### 6.3 交互与状态问题

1. 页面级状态覆盖不均匀，Skill 页面比其他页面更完整。
2. 一些提示采用情绪化符号与 emoji，不利于专业感统一。
3. 工作流中部分辅助内容没有为移动端提供同等级替代入口。

### 6.4 响应式问题

1. 创作页移动端通过隐藏双侧栏解决空间问题，但会损失流程可见性和辅助能力。
2. 首页卡片和技能条在窄屏下可用，但仍有内容密度和首屏节奏可优化空间。
3. 后台图表页在移动端缩成单列后，可读性策略还不够完整。

### 6.5 性能与可访问性问题

1. 图片、字体、图表与动画仍有进一步优化空间。
2. `prefers-reduced-motion` 有全局兜底，但尚未形成组件级预算与审查标准。
3. 图表页的可访问性策略需要补足文本摘要、空态、错误态和键盘可达性说明。

## 7. 优化总策略

### 7.1 先结构后美化

所有页面先做这 4 件事，再做“变高级”：

1. 明确页面角色
2. 明确主任务与主 CTA
3. 重排内容优先级
4. 补齐状态与反馈

### 7.2 先系统后页面

优化顺序不建议按“哪个页面最难看”推进，而建议按以下路径：

1. 设计 token
2. 核心布局与容器规则
3. 基础组件状态
4. 页面模板
5. 业务页面精修

### 7.3 先关键路径后外围页面

推荐优先级：

1. 首页
2. 创作页
3. Skill 中心与执行页
4. 文章详情页
5. 统计页
6. 会员页与管理页

## 8. 工作流与页面优化计划

### 8.1 首页优化计划

目标：提升理解速度、首屏行动率、真实感与品牌可信度。

实施项：

1. 把 Hero 从“口号 + 输入框”优化为“产品名 + 真实工作流暗示 + 明确 CTA”
2. 在首屏或首屏下方加入真实界面片段、流程预览或结果样例
3. 将“核心能力”从泛功能卡片改为更贴近结果的任务分组
4. 优化最近创作区的信息层级，让回访用户更快回到任务
5. 明确游客与登录用户的不同首屏路径

验收：

1. 首屏 5 秒测试能说清“是什么、给谁用、下一步是什么”
2. 主 CTA 只有一个主动作，次动作不争抢
3. 不依赖大量泛能力卡片建立可信度

### 8.2 创作页优化计划

目标：让多阶段创作流程更稳、更专注、更适配移动端。

实施项：

1. 将三栏布局梳理为“主工作区 + 可折叠辅助区”的逻辑，而非永久三栏
2. 重新定义左侧流程、右侧提示、实时日志的优先级
3. 为移动端提供可展开的流程抽屉、日志抽屉或分段辅助面板
4. 统一阶段标题、说明、等待态、确认态和出错态
5. 移除 emoji 和情绪化日志，改为专业状态反馈
6. 强化创建前、创建中、确认中、完成后四种大状态切换

验收：

1. 375 宽度下创作路径不丢功能、不丢关键上下文
2. 任何阶段用户都能知道“现在在哪一步、下一步是什么”
3. 失败和等待不是黑盒

### 8.3 Skill 页面优化计划

目标：让 Skill 从“功能卡片”进化成“明确任务 + 明确结果预期”的工具体验。

实施项：

1. 优化 Skill 卡片的结果预期表达，不只显示描述和阶段数
2. 统一输入表单布局、帮助信息、长度限制、默认值和提交反馈
3. 优化执行中界面的分区，让进度、流式预览和结果承接更清晰
4. 强化未知 Skill 的安全回退视图
5. 统一 Skill 的空态、错误态、登录态和恢复态语言

验收：

1. 用户进入任一 Skill 前能理解需要输入什么、会得到什么
2. 执行中状态能减少等待焦虑
3. 执行完成后的结果组件结构清晰、可复制、可复查

### 8.4 数据与后台页优化计划

目标：提升数据可读性、图表可信度和决策效率。

实施项：

1. 重排指标卡、趋势图、用户图、配额图的阅读顺序
2. 为图表补充文本摘要、空态、错误态和无数据提示
3. 降低装饰性悬浮效果，增强数据层级与说明信息
4. 统一数值格式、单位、时间范围和颜色角色
5. 审查图表颜色是否只靠颜色传达信息

验收：

1. 关键数据先于装饰出现
2. 图表即使加载失败，也有可用的替代反馈
3. 数据含义、周期和关系能被快速解释

## 9. 设计系统建设计划

### 9.1 Token 层

建立最小但可扩展的 token 体系：

1. 颜色：`canvas / surface / surface-muted / text / text-secondary / accent / success / warning / error`
2. 字体：标题、正文、标签、数字
3. 间距：`4 / 8 / 12 / 16 / 24 / 32 / 40 / 48`
4. 圆角：`sm / md / lg`
5. 阴影：`none / subtle / raised`
6. 动效：`fast / normal / emphasis`

### 9.2 组件层

优先统一这些组件：

1. 按钮
2. 输入框 / 文本域
3. 标签 / 状态徽标
4. 卡片 / 面板
5. 列表项 / 工具卡
6. 空状态 / 错误态
7. 进度组件
8. 图表容器

### 9.3 页面模板层

至少沉淀 4 套模板：

1. Hero + 首屏操作模板
2. 工具目录模板
3. 多阶段工作流模板
4. 后台分析模板

## 10. 可访问性计划

必须纳入 P0 或 P1 的项：

1. 统一 `focus-visible` 样式
2. 核心控件可键盘操作
3. 表单错误贴近字段，并支持页顶汇总
4. 实时状态使用合适的 `aria-live`
5. 图表区域补充文字摘要
6. 控件尺寸与间距满足触控目标
7. 所有动画遵守 reduced-motion

验收清单：

1. 仅用键盘能完成核心流程
2. 焦点不会消失或被裁切
3. 错误提示有恢复路径
4. 颜色不是唯一信息渠道

---

## 11. 响应式计划

### 11.1 断点策略

推荐按以下主要断点验证：

1. `375`
2. `768`
3. `1024`
4. `1440`

### 11.2 响应式治理原则

1. 不是简单缩小，而是重排任务顺序
2. 优先保留主任务与主反馈
3. 辅助信息可折叠，但不能凭空消失
4. 图表、列表、长文、日志都要有移动端策略

---

## 12. 性能计划

### 12.1 目标

1. 降低首屏渲染压力
2. 降低布局抖动
3. 减少非必要动画与重排
4. 控制图片、图表、字体与长列表的成本

### 12.2 实施项

1. 审查图片尺寸声明与懒加载策略
2. 优化字体使用和加载策略
3. 控制首屏渲染体积
4. 让图表按可见性或页面需求延迟初始化
5. 为大内容区与流式结果预留稳定空间，降低 CLS

## 15. 风险与回避策略

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 只改视觉不改结构 | 看起来焕新，实际体验没变 | 先做任务流和页面层级审计 |
| 单一页面最优，整站割裂 | 各页各自好看但不统一 | 先做 token 和模板层 |
| 移动端通过隐藏解决问题 | 桌面好看，手机缺功能 | 为侧栏与辅助信息设计替代容器 |
| 页面越来越卡片化 | 组件安全但模板感重 | 只在真正需要边界时使用卡片 |
| 过度追求动效 | 漂亮但性能和可用性受损 | 设定明确动效预算 |
