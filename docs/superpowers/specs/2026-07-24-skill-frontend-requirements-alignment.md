> 依据：`2026-07-24-skill-frontend-design.md`、现有 Vue 前端与 Skill 后端实现
> 状态：已确认并冻结

## 1. 体验简报（推荐基线）

| 字段 | 推荐决策 |
| --- | --- |
| 产品形态 | 面向内容创作者的高频操作型 AI 工具工作台 |
| 核心用户 | 已登录、已有明确写作任务，希望快速得到可复用结果的内容创作者 |
| 核心动作 | 选择 Skill，提交输入，理解执行进度，检查并带走结果 |
| 信任证据 | 真实的阶段进度、审校前后对比、结构化选题与可复制的最终内容 |
| 页面角色 | 激活与操作，不承担营销落地页职责 |
| 视觉方向 | Precision system：清晰网格、克制绿色、较高信息密度、强调结果本身 |
| 交互预算 | 克制的状态动效；唯一重点交互为审校前后差异检查 |
| 技术约束 | Vue 3、TypeScript、Ant Design Vue、现有 CSS 变量与图标库，不新增纯视觉依赖 |

## 2. 已从代码确认的事实

- 当前前端使用 Vue 3、Vue Router、Pinia、Ant Design Vue 和 `@ant-design/icons-vue`。
- 当前路由只对 `/admin` 做前端守卫，Skill 路由的登录控制需要新增。
- 后端已注册 `proofreading`、`topic-gen`、`article-to-x`、`research` 四个 Skill。
- `proofreading` 实际包含一个 `requireConfirmation: true` 的阶段，和“首批简化为单轮”的文档描述存在冲突。
- 当前 SSE 流式片段是纯文本 `STREAMING:` 前缀，不是文档示例中的 JSON `skill.progress` 消息。
- 当前结果接口没有返回 `outputData`，完成消息也不携带结果；前端暂时无法渲染最终结果。
- 当前数据库只保存最后阶段输出，无法直接构造审校文档中设想的“三遍完整结果”。
- 当前变量定义只有名称、描述、必填和来源，没有字段类型、选项、默认值、长度限制等 UI 元数据。
- 当前执行接口先创建一个 executionId 返回给前端，异步服务随后又创建了另一个 executionId 执行和落库；SSE、结果查询与真实任务因此无法用同一 ID 关联。
- 当前状态图没有读取 `requireConfirmation`，`confirm` 接口也只记录日志，不会暂停、恢复或改变执行状态；现有“多轮确认”尚未形成可用协议。

## 4. 需求决策问题（61 题）

### A. 范围、用户与信息架构

#### Q01 首期 Skill 范围是什么？
- **A（推荐）：只正式开放 proofreading、topic-gen、article-to-x。** 优点：严格贴合规格，测试范围可控；缺点：已存在的 research 暂时不露出。
- **B：四个 Skill 全部开放，包含 research。** 优点：后端能力利用更完整；缺点：需要补 research 专属结果、确认流程和额外测试。

#### Q02 用户可见的功能名称是什么？
- **A（推荐）：导航叫“AI 工具”，页面标题叫“AI 技能中心”。** 优点：用户易懂，同时保留 Skill 概念；缺点：同一能力有两种称呼。
- **B：统一叫“技能 / Skill”。** 优点：术语一致、贴近技术模型；缺点：普通创作者理解成本略高。

#### Q03 首期核心用户优先级是什么？
- **A（推荐）：已有文章或明确方向的高频内容创作者。** 优点：流程可围绕效率和结果检查优化；缺点：对首次体验用户的引导较少。
- **B：没有写作经验的新用户。** 优点：上手更友好；缺点：需要更多解释、示例和引导步骤，界面更重。

#### Q04 Skill 中心是否必须登录后才能查看？
- **A（推荐）：列表可查看，执行时要求登录。** 优点：用户能先了解能力，直接链接也更友好；缺点：要处理游客态 CTA 和登录回跳。
- **B：访问 `/skill` 即要求登录。** 优点：权限模型简单；缺点：未登录用户无法预览产品能力。

#### Q05 首页“AI 工具箱”如何呈现？
- **A（推荐）：作为创作入口后的紧凑工具带，展示 3 个 Skill。** 优点：不抢主创作任务，仍有足够发现性；缺点：首页内容会增加一屏左右。
- **B：把工具箱提升为首页首屏主入口。** 优点：Skill 曝光最大；缺点：会削弱现有“输入主题开始创作”的核心动作。

#### Q06 路由结构是否沿用规格？
- **A（推荐）：使用 `/skill` 与 `/skill/:skillName`。** 优点：改动少、链接简洁；缺点：英文单数路径与中文产品语义略弱。
- **B：改为 `/tools` 与 `/tools/:skillName`。** 优点：用户语义更直观；缺点：偏离规格并需要统一文档与后端跳转约定。

#### Q07 未登录用户打开 Skill 深链时如何处理？
- **A（推荐）：保留完整 redirect，登录后返回原 Skill。** 优点：任务连续，转化损耗小；缺点：路由守卫和登录页要可靠传递参数。
- **B：统一登录后回首页。** 优点：实现简单；缺点：用户需要重新寻找刚才的 Skill。

#### Q08 Skill 不存在时如何处理？
- **A（推荐）：执行页内展示 404 空状态并提供返回技能中心。** 优点：上下文清楚、不会突然跳页；缺点：需维护页面级错误态。
- **B：自动跳回 `/skill` 并弹 toast。** 优点：实现较快；缺点：错误原因短暂，深链体验较突兀。

#### Q09 Skill 列表默认排序是什么？
- **A（推荐）：按工作流排序：选题生成、文章审校、社交转写。** 优点：符合创作生命周期；缺点：不是按名称或热度排序。
- **B：按后端返回顺序。** 优点：前端零配置，新增 Skill 自动出现；缺点：展示顺序不可控且可能随实现变化。

#### Q10 分类筛选首期如何处理？
- **A（推荐）：保留“全部 / 写作”，只有 research 开放后再显示“调研”。** 优点：不展示空筛选项；缺点：首期只有一个实际分类，筛选价值有限。
- **B：始终显示“全部 / 写作 / 调研”。** 优点：为扩展预留稳定结构；缺点：首期“调研”可能为空或暴露未完成能力。

### B. Skill 中心体验

#### Q11 首期需要搜索 Skill 吗？
- **A（推荐）：不加搜索，列表超过 8 个再引入。** 优点：界面简洁、减少无效控件；缺点：扩展后需要再开发。
- **B：首期加入即时搜索。** 优点：架构提前完整；缺点：3 个条目时显得冗余，也增加状态与测试。

#### Q12 Skill 卡片的点击区域是什么？
- **A（推荐）：整张卡可点击，并保留明确“打开”图标按钮。** 优点：高效且有清楚动作提示；缺点：需处理卡内未来可能出现的次级操作。
- **B：只有“使用”按钮可点击。** 优点：交互边界明确；缺点：点击目标更小，浏览效率较低。

#### Q13 卡片展示哪些元数据？
- **A（推荐）：名称、说明、阶段数、预计交互类型，不展示模型名。** 优点：信息与用户决策直接相关；缺点：技术透明度较低。
- **B：额外展示模型、是否流式、角色要求。** 优点：信息完整；缺点：卡片过密，普通用户不一定理解。

#### Q14 Skill 图标从哪里来？
- **A（推荐）：用现有 Ant Design 图标并配置语义色。** 优点：无需新增资源、风格一致、加载稳定；缺点：品牌独特性有限。
- **B：为每个 Skill 制作专属位图插画。** 优点：识别度和视觉表现更强；缺点：需要额外资产生产，工具页面可能显得偏营销。

#### Q15 暂不可用的 Skill 是否展示？
- **A（推荐）：仅展示后端返回且前端支持的 Skill。** 优点：所有可见主动作都可用；缺点：无法提前宣传未来能力。
- **B：展示“即将上线”卡片。** 优点：可传达路线图；缺点：产生不可操作项并占据视觉注意力。

#### Q16 Skill 列表加载态是什么？
- **A（推荐）：使用与最终网格尺寸一致的骨架行。** 优点：布局稳定、感知速度好；缺点：要为响应式维护骨架样式。
- **B：页面中央使用 Spin。** 优点：实现简单；缺点：信息结构暂时消失，页面易抖动。

#### Q17 列表为空时提供什么动作？
- **A（推荐）：说明暂不可用，并提供“刷新”按钮。** 优点：用户能自助恢复临时错误；缺点：真实配置为空时刷新无效。
- **B：只显示“暂无技能”。** 优点：最简洁；缺点：没有恢复路径，也无法区分空数据和请求失败。

#### Q18 中心页首屏采用哪种布局？
- **A（推荐）：紧凑标题区 + 筛选栏 + 真实 Skill 网格，下一行在首屏可见。** 优点：进入即能操作，符合工作台定位；缺点：视觉戏剧性较弱。
- **B：大面积 Hero 后再展示卡片。** 优点：品牌表达空间更大；缺点：核心工具被推到首屏以下，操作效率降低。

### C. 动态输入表单与执行

#### Q19 动态表单类型由谁定义？（关键契约）
- **A（推荐）：后端变量增加 `uiType/options/defaultValue/placeholder/maxLength` 元数据。** 优点：可扩展、无需前端猜测、后续新增 Skill 真正零改动；缺点：需要同步修改后端 YAML 和类型。
- **B：沿用规格，在前端按变量名推断。** 优点：无需后端改动、能快速上线；缺点：脆弱，变量改名或新类型会渲染错误。

#### Q20 在后端 UI 元数据补齐前如何推进？
- **A（推荐）：前端建立显式 Skill 字段配置表，并保留通用 fallback。** 优点：首期结果可控，也能兼容未知 Skill；缺点：配置在前后端重复。
- **B：完全使用名称推断，不维护 Skill 特例。** 优点：代码量更少；缺点：选项、默认值、帮助文案很难准确。

#### Q21 可选字段的默认值是什么？
- **A（推荐）：style 默认“自动匹配”，platform 默认“微博”，并允许修改。** 优点：减少首次操作成本；缺点：默认平台可能不符合所有用户意图。
- **B：所有可选字段保持未选择。** 优点：不替用户做假设；缺点：结果不确定，用户需要更多决策。

#### Q22 风格选项如何显示？
- **A（推荐）：中文标签 + 保持英文 API 值，例如“科技 / tech”。** 优点：用户易懂且不破坏后端契约；缺点：要维护标签映射。
- **B：直接显示后端英文值。** 优点：实现和调试直接；缺点：中文产品中体验生硬。

#### Q23 文章内容输入区支持什么来源？
- **A（推荐）：支持粘贴与从当前文章上下文预填，首期不做文件上传。** 优点：覆盖主要路径、复杂度可控；缺点：独立页面不能导入本地文档。
- **B：增加 Markdown/TXT 文件上传。** 优点：长文导入更高效；缺点：增加文件解析、编码、大小与安全处理。

#### Q24 长文本长度如何控制？
- **A（推荐）：前端显示实时字符数和软提示，服务端决定硬限制。** 优点：避免前后端限制漂移；缺点：超长内容可能到提交后才被拒绝。
- **B：前端固定硬限制 20,000 字符。** 优点：反馈即时、请求可控；缺点：数字可能与模型或后端实际能力不一致。

#### Q25 输入草稿是否自动保存？
- **A（推荐）：按 `skillName` 保存到 sessionStorage，成功执行后清理。** 优点：刷新或误跳转时可恢复，隐私生命周期较短；缺点：同一标签页会保留用户文本。
- **B：不保存草稿。** 优点：实现简单且不留本地内容；缺点：刷新或登录跳转会丢失长文本。

#### Q26 表单校验何时出现？
- **A（推荐）：失焦后校验，提交时聚焦第一个错误字段。** 优点：反馈及时又不过度打扰；缺点：实现比仅提交校验略复杂。
- **B：只在点击执行后校验。** 优点：规则实现简单；缺点：长表单中定位错误更慢。

#### Q27 主执行按钮如何命名？
- **A（推荐）：使用动作化文案，如“开始审校 / 生成选题 / 转为社交文案”。** 优点：意图清晰、有领域感；缺点：需要维护 Skill 文案配置。
- **B：所有页面统一“执行 Skill”。** 优点：通用组件最简单；缺点：技术化且缺少任务语义。

#### Q28 完成后如何重新开始？
- **A（推荐）：提供“调整输入”返回原表单，保留内容与选项。** 优点：迭代成本低；缺点：状态机需要支持 COMPLETED 回到 INPUT。
- **B：提供“新建执行”并清空表单。** 优点：状态简单；缺点：微调重跑时需要重新输入。

#### Q29 执行中离开页面如何处理？
- **A（推荐）：弹出确认，说明任务仍会在后台运行并可通过本次链接恢复。** 优点：避免误操作，也尊重后台异步事实；缺点：需要可靠持久化 executionId。
- **B：允许直接离开，不做提示。** 优点：导航自由、实现简单；缺点：用户可能误以为任务被取消或找不到结果。

#### Q30 同一执行页是否允许并发启动？
- **A（推荐）：单页一次只保留一个执行，运行时禁用再次提交。** 优点：状态明确、避免重复消耗；缺点：高级用户不能从同页并行尝试。
- **B：允许产生多个执行标签。** 优点：可并行比较结果；缺点：状态、SSE 和恢复逻辑复杂度显著增加。

### D. 进度、SSE 与恢复

#### Q31 进度如何表达？
- **A（推荐）：阶段步骤条 + 当前阶段状态 + 细进度线，不伪造百分比。** 优点：真实反映离散阶段；缺点：单阶段 Skill 的视觉变化较少。
- **B：显示 0-100% 百分比进度条。** 优点：用户熟悉、反馈直观；缺点：后端没有真实百分比，只能估算。

#### Q32 流式内容显示在哪里？
- **A（推荐）：当前阶段下方使用固定高度的实时预览区，完成后折叠为阶段摘要。** 优点：有过程反馈且不抢最终结果；缺点：需处理自动滚动和折叠状态。
- **B：直接在最终结果区域持续追加。** 优点：实现直接；缺点：阶段切换时内容容易混合，结构不稳定。

#### Q33 阶段名称如何呈现？
- **A（推荐）：维护中文业务标签映射，未知阶段回退格式化英文名。** 优点：首期体验自然且保留扩展能力；缺点：多一份文案配置。
- **B：直接展示 `content_review` 等后端名称。** 优点：无需映射、便于调试；缺点：用户体验技术化。

#### Q34 完成后的界面切换方式是什么？
- **A（推荐）：保留完成的阶段摘要，在同页下方平滑揭示结果。** 优点：过程与结果连续，便于理解耗时；缺点：页面会变长。
- **B：完成后完全替换执行区为结果。** 优点：结果聚焦、界面简洁；缺点：过程信息丢失，调试和信任感较弱。

#### Q35 结果接口是否允许同步补齐 `outputData`？（关键契约）
- **A（推荐）：允许最小后端修改，结果接口返回解析后的 `outputData`。** 优点：真实结果可恢复、刷新后可展示；缺点：本次范围会包含一个后端契约改动。
- **B：严格只改前端。** 优点：职责边界清楚；缺点：当前完成消息和结果接口均无结果内容，定制结果页无法真实工作。

#### Q36 proofreading 是否返回全部阶段输出？（关键契约）
- **A（推荐）：持久化并返回 `reviewResult/polishedContent/finalContent`。** 优点：能实现规格中的三遍审校和前后对比；缺点：需要调整执行结果存储结构。
- **B：只返回最后的 `finalContent`。** 优点：后端改动最小；缺点：无法展示内容审校问题和中间改写对比。

#### Q37 SSE 消息格式采用哪种？（关键契约）
- **A（推荐）：后端统一发送 JSON 事件，流式片段使用 `skill.progress` + `data`。** 优点：类型安全、可扩展、与设计文档一致；缺点：需要改后端流式发送逻辑。
- **B：前端同时兼容 JSON 与 `STREAMING:` 纯文本。** 优点：无需立即改后端；缺点：协议分叉，异常解析和维护成本更高。

#### Q38 SSE 断线如何重试？
- **A（推荐）：指数退避自动重连 1 次，再切换 2 秒轮询结果。** 优点：短暂网络波动可恢复，失败后仍能得到结果；缺点：实现和测试复杂度较高。
- **B：只自动重连 1 次，失败即提示手动刷新。** 优点：逻辑简单；缺点：长任务在不稳定网络中体验较差。

#### Q39 刷新后如何恢复执行？
- **A（推荐）：URL 带 `executionId` 查询参数并同步保存 sessionStorage。** 优点：链接可恢复且标签页内可靠；缺点：URL 更长，并需清理过期 ID。
- **B：仅保存 sessionStorage。** 优点：URL 干净；缺点：分享链接或跨标签页无法恢复。

#### Q40 10 分钟超时后怎么做？
- **A（推荐）：停止 SSE，转为低频轮询，并显示“任务仍在后台运行”。** 优点：不误报失败，仍可最终拿到结果；缺点：页面状态持续时间更长。
- **B：标记失败并提供重试。** 优点：状态收敛快；缺点：可能重复启动仍在运行的任务并产生额外消耗。

#### Q41 错误信息展示到什么程度？
- **A（推荐）：用户可读摘要 + 可展开的 executionId，不直接展示服务端堆栈。** 优点：清楚且安全，便于报障；缺点：开发调试需要查日志。
- **B：直接展示后端 `errorMessage` 全文。** 优点：开发阶段定位快；缺点：可能泄露内部实现或出现难懂技术信息。

#### Q42 未识别结果结构如何处理？
- **A（推荐）：默认结果组件支持 Markdown、JSON 树和纯文本三种安全回退。** 优点：未知 Skill 仍可用；缺点：需要结果类型检测和安全渲染。
- **B：一律转成纯文本。** 优点：最稳妥、实现简单；缺点：结构化结果可读性差。

### E. 三类结果体验

#### Q43 proofreading 的主结果布局是什么？
- **A（推荐）：顶部问题摘要，中部差异检查，底部最终稿。** 优点：符合“发现问题 → 理解修改 → 使用结果”的心智顺序；缺点：完整页面较长。
- **B：使用三个等权 Tabs。** 优点：页面紧凑；缺点：重要信息被分隔，用户可能跳过中间过程。

#### Q44 审校差异采用什么粒度？
- **A（推荐）：句子/段落级高亮增删，不做字符级噪声。** 优点：长文更易读，适合内容编辑；缺点：细小标点改动不够突出。
- **B：字符级 diff。** 优点：变化最精确；缺点：中文长文容易出现大量碎片高亮。

#### Q45 最终审校稿能否直接编辑？
- **A（推荐）：首期只读，提供复制和导出，后续再接编辑保存。** 优点：避免“编辑后保存到哪里”的数据边界问题；缺点：用户需到外部编辑器继续修改。
- **B：结果区内直接编辑。** 优点：闭环体验更强；缺点：需要草稿状态、撤销、保存目标和离开确认。

#### Q46 审校评分如何处理？
- **A（推荐）：只有后端明确返回评分时才展示，不在前端推算。** 优点：不制造虚假精度；缺点：当前可能没有醒目的总体指标。
- **B：前端根据问题数量计算评分。** 优点：结果更有仪表感；缺点：算法武断，可能误导用户。

#### Q47 结果导出格式是什么？
- **A（推荐）：复制纯 Markdown + 下载 `.md`。** 优点：与现有文章导出能力一致、实现稳定；缺点：不直接支持 Word。
- **B：同时支持 Markdown、纯文本和 Word。** 优点：覆盖更多工作流；缺点：Word 生成和排版验收显著扩大范围。

#### Q48 topic-gen 选题如何布局？
- **A（推荐）：单列可比较列表，展开查看大纲与优劣。** 优点：长标题和大纲在桌面、移动端都易扫读；缺点：同时看到的选题数量较少。
- **B：桌面 2-3 列卡片网格。** 优点：视觉丰富、横向比较快；缺点：内容密度高时卡片高度不齐，移动端需要完全重排。

#### Q49 点击“使用此选题”后做什么？
- **A（推荐）：跳转 `/create` 并预填标题/方向，同时保留返回结果的能力。** 优点：形成真实创作闭环；缺点：要明确 query 或 store 的数据传递。
- **B：只 emit 给当前父组件，不主动导航。** 优点：组件纯粹、嵌入场景灵活；缺点：独立 Skill 页面动作完成后缺少下一步。

#### Q50 topicOptions 数据结构由谁保证？（关键契约）
- **A（推荐）：后端定义稳定 DTO：title/type/workload/outline/pros/cons。** 优点：结果组件类型安全、空字段可控；缺点：需要规范 LLM 输出并校验。
- **B：前端适配任意 JSON。** 优点：后端自由度高；缺点：展示逻辑复杂，模型输出变化容易破版。

#### Q51 article-to-x 使用什么布局？
- **A（推荐）：桌面左右对照，移动端结果优先、原文摘要可折叠。** 优点：桌面可比较，移动端直接聚焦可复制内容；缺点：需要两个响应式信息顺序。
- **B：所有尺寸都使用上下布局。** 优点：实现简单、阅读宽度稳定；缺点：桌面横向空间利用不足。

#### Q52 “重新生成”如何定义？
- **A（推荐）：保留输入与选项，创建新的 executionId，并明确会消耗一次执行。** 优点：行为清楚、历史执行互不覆盖；缺点：需要防止快速重复点击。
- **B：复用原 executionId 覆盖结果。** 优点：界面只维护一个记录；缺点：与当前后端执行模型不符，也丢失历史结果。

#### Q53 社交结果是否提供平台专属辅助？
- **A（推荐）：显示字符数和目标平台标签，不自动添加未确认的话题标签。** 优点：实用且不虚构内容；缺点：平台优化能力显得克制。
- **B：自动补充 hashtags、emoji 和发布提示。** 优点：更像完整发布助手；缺点：可能偏离用户语气，且 emoji 与当前设计约束冲突。

### F. 创作流程嵌入

#### Q54 SkillLauncher 使用 Modal 还是 Drawer？
- **A（推荐）：桌面右侧宽 Drawer，移动端全屏 Drawer。** 优点：保留文章上下文、长结果滚动更自然；缺点：偏离原规格中的 Modal。
- **B：使用大尺寸 Modal。** 优点：与规格一致、Ant Design 实现直接；缺点：长文本和移动端空间较局促。

#### Q55 执行中关闭 Launcher 怎么处理？
- **A（推荐）：允许最小化为页面内运行状态条，任务继续执行。** 优点：不阻断主流程且能返回结果；缺点：需要父级管理执行状态。
- **B：关闭前弹确认，确认后只关闭界面，任务后台继续。** 优点：实现较简单；缺点：用户关闭后可能不知道从哪里恢复。

#### Q56 嵌入式结果如何回传？
- **A（推荐）：结构化 emit 结果，同时保留复制/导出；父页面不自动覆盖文章。** 优点：安全、可扩展、不破坏原文；缺点：完成后仍需用户决定如何使用。
- **B：完成后自动替换当前文章内容。** 优点：操作步骤少；缺点：高风险，需要撤销、保存和版本机制。

### G. 视觉、动效、响应式与验收

#### Q57 主视觉方向是什么？
- **A（推荐）：精密工作台风格，白/浅灰画布、深色文字、绿色动作色、琥珀提示色。** 优点：与现有品牌兼容且避免单一绿色主题；缺点：视觉表达相对克制。
- **B：延续现有较强渐变和毛玻璃卡片风格。** 优点：与当前首页表面风格最接近；缺点：工具页面层级容易模糊，卡片和透明效果可能过多。

#### Q58 动效预算是什么？
- **A（推荐）：只做状态反馈、结果揭示与 Drawer 连续性，并支持 reduced-motion。** 优点：性能稳定、注意力聚焦任务；缺点：整体观感不追求强展示性。
- **B：加入卡片级联、滚动揭示和更丰富进度动画。** 优点：视觉更活跃；缺点：长任务中容易分散注意力，也增加无障碍和性能成本。

#### Q59 移动端全局导航如何容纳“AI 工具”？
- **A（推荐）：保留图标导航，但在窄于 480px 时收纳低频项到“更多”菜单。** 优点：触控目标稳定、不会挤压用户区；缺点：部分入口多一次点击。
- **B：继续横向显示全部图标。** 优点：所有入口一步可达；缺点：新增 Skill 后 375px 宽度很容易拥挤或溢出。

#### Q60 首期验收标准采用哪一级？
- **A（推荐）：类型检查 + 构建 + 关键状态组件测试 + 1440/768/375 视觉截图 + 键盘与 reduced-motion 手测。** 优点：覆盖功能、响应式与无障碍核心风险；缺点：需要补测试基础设施或轻量脚本。
- **B：只通过 `npm run build` 和人工桌面浏览。** 优点：交付更快；缺点：SSE 状态、移动端溢出和键盘问题容易漏检。

### H. 多轮确认协议

#### Q61 首期如何处理 `requireConfirmation`？（关键契约）
- **A（推荐）：首期三个公开 Skill 均按单轮任务执行，YAML 暂时关闭确认标记；结果页中的“使用此选题”等操作只消费结果，不恢复原执行。** 优点：与当前状态图能力及首期规格一致，任务可稳定完成并恢复；缺点：暂不支持阶段中暂停、修改后继续。
- **B：本期实现真正的 `WAITING_CONFIRMATION` 状态、确认数据持久化和暂停/恢复协议。** 优点：完整发挥多轮 Skill 设计，后续流程扩展更自然；缺点：需要重构状态图执行、超时、并发、SSE 重连和恢复语义，显著扩大本期后端及测试范围。

## 5. 推荐决策下的实施边界

确认全部推荐后，首期将采用以下边界：

1. 正式开放 3 个 Skill，保留未知 Skill 的安全回退能力。
2. Skill 中心和执行页以操作效率为主，不制作营销型 Hero 或装饰性插画。
3. 动态表单首期使用显式配置 + fallback，同时推动后端补 UI 元数据。
4. 允许最小后端契约修正：结构化 SSE、返回结果数据、持久化 proofreading 全阶段输出。
5. 三类结果分别采用审校纵向工作流、选题单列比较、社交文案响应式对照。
6. 嵌入式执行使用响应式 Drawer，不自动覆盖原文章。
7. 按 1440、768、375 三档完成视觉、交互、无障碍与构建验收。
