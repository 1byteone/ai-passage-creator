# 灵犀写作｜多智能体编排与系统设计项目复盘

## 1. 这一项职责在项目中的定位

- 我负责的是整条 AI 图文生成链路的后端编排设计。
- 核心目标不是“调一次模型出结果”，而是把文章生成拆成多个可控制、可扩展、可观测的执行节点。
- 在本项目里，我基于 `StateGraph` 将流程拆成：
  - 标题生成
  - 大纲生成
  - 正文生成
  - 配图需求分析
  - 并行配图生成
  - 图文合成

一句话面试表达：

> 我把 AI 图文生成从单次大模型调用，升级成了基于 `StateGraph` 的多智能体工作流，把复杂链路拆成可编排节点，既提升了可维护性，也为后续扩展审核、润色、重试等能力预留了结构空间。

---

## 2. 功能描述

### 业务目标

- 用户输入一个选题后，系统不是直接返回整篇文章，而是按创作流程逐步生成。
- 这样做的好处有两个：
  - 生成结果更可控，用户能在标题和大纲阶段参与确认
  - 每个阶段职责单一，便于定位问题和横向扩展

### 后端职责

- 定义每个 Agent 的输入输出边界
- 设计阶段之间的状态流转
- 组织串行/并行执行关系
- 对最终结果做统一汇总并持久化

---

## 3. 业务流程

### 总流程

1. 用户创建文章任务
2. 系统进入 Phase1：生成标题候选
3. 用户确认标题
4. 系统进入 Phase2：生成结构化大纲
5. 用户确认或调整大纲
6. 系统进入 Phase3：生成正文、分析配图需求、生成图片、合成图文
7. 最终落库完整文章内容

### Phase3 的编排流程

1. `ContentGeneratorAgent` 生成正文
2. `ImageAnalyzerAgent` 识别哪些位置需要插图
3. `ParallelImageGenerator` 并发生成或检索图片
4. `ContentMergerAgent` 将图片 URL 替换到正文占位符中

---

## 4. 核心设计

### 4.1 为什么用多智能体编排，而不是一个大 Service 写到底

- 如果所有逻辑塞进一个 Service：
  - 代码会迅速膨胀
  - 阶段状态不清晰
  - 后续想扩展审核/润色/敏感词过滤时改动面大

- 改成图编排后：
  - 节点职责更单一
  - 边定义了执行顺序
  - 后续加节点比改大方法更安全

### 4.2 状态设计

项目里用 `ArticleState` 作为智能体间共享状态，承接：

- `taskId`
- `topic`
- `style`
- `titleOptions`
- `title`
- `outline`
- `content`
- `imageRequirements`
- `images`
- `fullContent`

设计重点：

- 不是让 Agent 之间直接相互调用
- 而是让它们通过共享状态对象解耦协作

## 5. 代码窗口

### 5.1 核心编排器

```java
@Service
public class ArticleAgentOrchestrator {

    public void executePhase1_GenerateTitles(ArticleState state, Consumer<String> streamHandler) {
        StateGraph graph = buildPhase1Graph();
        OverAllState finalState = graph.compile().invoke(inputs).orElseThrow();
        List<ArticleState.TitleOption> titleOptions =
                (List<ArticleState.TitleOption>) finalState.value("titleOptions").orElse(null);
        state.setTitleOptions(titleOptions);
    }

    public void executePhase2_GenerateOutline(ArticleState state, Consumer<String> streamHandler) {
        StreamHandlerContext.set(streamHandler);
        StateGraph graph = buildPhase2Graph();
        OverAllState finalState = graph.compile().invoke(inputs).orElseThrow();
        ArticleState.OutlineResult outline = convertOutline(finalState);
        state.setOutline(outline);
    }

    public void executePhase3_GenerateContent(ArticleState state, Consumer<String> streamHandler) {
        StreamHandlerContext.set(streamHandler);
        StateGraph graph = buildPhase3Graph();
        OverAllState finalState = graph.compile().invoke(inputs).orElseThrow();
        state.setContent(finalState.value("content").map(Object::toString).orElse(null));
        state.setImageRequirements((List<ArticleState.ImageRequirement>) finalState.value("imageRequirements").orElse(null));
        state.setImages((List<ArticleState.ImageResult>) finalState.value("images").orElse(null));
        state.setFullContent(finalState.value("fullContent").map(Object::toString).orElse(null));
    }
}
```

### 5.2 Phase3 图编排

```java
private StateGraph buildPhase3Graph() throws GraphStateException {
    return new StateGraph(createKeyStrategyFactory())
            .addNode("content_generator", node_async(contentGeneratorAgent))
            .addNode("image_analyzer", node_async(imageAnalyzerAgent))
            .addNode("parallel_image_generator", node_async(parallelImageGenerator))
            .addNode("content_merger", node_async(contentMergerAgent))
            .addEdge(START, "content_generator")
            .addEdge("content_generator", "image_analyzer")
            .addEdge("image_analyzer", "parallel_image_generator")
            .addEdge("parallel_image_generator", "content_merger")
            .addEdge("content_merger", END);
}
```

## 6. 面试官感兴趣的亮点

### 亮点一：把“AI 调用”做成“工作流编排”

面试官为什么会感兴趣：

- 说明你不是只会写 Controller 调模型
- 说明你有架构抽象能力

怎么回答：

> 我没有把内容生成当成一次 RPC，而是把它抽象为多阶段工作流。每个 Agent 只关心自己的输入输出，状态通过 `ArticleState` 传递，整体由 `StateGraph` 驱动。这样后续如果要插入审核、重试、人工干预节点，改动会非常小。

### 亮点二：串行与并行混合编排

怎么回答：

> 标题、大纲、正文这些阶段是强依赖的，所以采用串行；但配图生成之间不存在强依赖，因此在第三阶段内部做了并发化处理。这样既保证了业务正确性，也兼顾了执行效率。

### 亮点三：为扩展能力预留结构

怎么回答：

> 我在设计时就按“节点 + 状态 + 边”的方式组织，而不是按“页面接口”组织。所以如果未来需要扩展成微服务，或者把图编排换成 MQ 驱动，迁移成本也相对可控。

## 7. 面试常问问题与应对回答

### Q1：为什么要拆成多个 Agent？一个大模型一次生成不行吗？

回答思路：

- 可以做，但不可控
- 一次性生成全文容易出现偏题、结构混乱、结果无法局部修改
- 拆成多个 Agent 后，每个节点职责更清晰，也方便重试和回放

标准回答：

> 技术上一次调用可以完成，但工程上不合适。因为文章创作天然有标题、大纲、正文、配图几个阶段，拆开后既能让用户参与确认，也能显著提升可维护性和可追踪性。

### Q2：`StateGraph` 相比普通 if-else 流程代码，优势在哪？

回答思路：

- 执行顺序显式
- 节点职责清晰
- 未来新增节点更容易

标准回答：

> 如果用普通 Service 串逻辑，早期开发快，但后期扩展成本会越来越高。`StateGraph` 的优势是把流程结构显式化了，特别适合这种多阶段、可扩展的 AI 工作流。

### Q3：Agent 之间怎么通信？为什么不直接互相调用？

回答思路：

- 通过共享状态对象通信
- 降低节点之间耦合

标准回答：

> 我采用的是共享状态模型，而不是 Agent 直接相互调用。这样每个节点只依赖输入状态，不依赖上一个节点的实现细节，整体更容易测试和替换。

### Q4：如果后面要加“文章审核 Agent”，你怎么做？

标准回答：

> 我会把审核能力做成独立节点，插在正文生成后、图文合成前。它读取 `content`，输出审核结果或修订后的内容，然后再进入下一节点。因为现在已经是图编排结构，所以加节点成本比较低。

### Q5：你这个编排设计最大的 trade-off 是什么？

标准回答：

> trade-off 是引入了一层工作流抽象，开发复杂度会比简单串行 Service 高一点；但对于这个项目来说，后续扩展性、可维护性和可观测性收益更大，所以是值得的。

## 8. 面试收尾话术

> 这部分我做的核心价值，是把 AI 图文生成从“单点能力调用”提升成了“工作流系统设计”。我不是简单接了一个模型，而是设计了阶段化、多智能体协作的执行框架，让系统在后续扩展、问题定位和性能优化上都有更好的基础。
