# 灵犀写作｜异步与高并发处理项目复盘

## 1. 这一项职责在项目中的定位

- 文章生成、图片生成、本质上都是长耗时任务。
- 如果把这些逻辑同步阻塞在接口线程里，接口 RT 会非常长，用户体验和系统吞吐都会很差。
- 所以我负责把整条生成链路改造成“快速受理 + 后台异步执行 + 前端实时感知”的模式。

一句话面试表达：

> 我基于 `ThreadPoolTaskExecutor + @Async` 把长耗时 AI 任务异步化，并结合任务状态管理和 SSE 实时回调，实现了接口快速返回、后台执行、前端可观测的高并发处理模型。

---

## 2. 功能描述

### 业务问题

- 用户点击生成文章后，后端要经历：
  - 大模型生成标题
  - 大模型生成大纲
  - 大模型生成正文
  - 图片检索 / 生图
  - 图文合成

这些步骤累计起来很容易达到几十秒。

### 我的目标

- 让创建接口快速返回 `taskId`
- 后台异步执行各阶段任务
- 前端实时收到进度消息，而不是一直转圈
- 在并发场景下尽量避免线程被耗尽

---

## 3. 业务流程

### 创建任务链路

1. 用户请求创建文章
2. 后端完成参数校验、登录校验、配额校验
3. 创建文章任务记录
4. 立即返回 `taskId`
5. 异步线程池接管标题生成任务
6. 用户通过 SSE 查看进度

### 阶段执行链路

1. Phase1 完成后，前端拿到标题候选
2. 用户确认标题，触发 Phase2 异步执行
3. Phase2 完成后，用户确认大纲
4. Phase3 异步执行正文+配图
5. 最终状态变更为 `COMPLETED`

---

## 4. 核心设计

### 4.1 为什么不用同步接口

- 同步接口会导致：
  - Tomcat 工作线程长期占用
  - 前端超时风险大
  - 服务端线程数上不去，吞吐受限

### 4.2 异步线程池设计

当前项目线程池配置：

- 核心线程数：5
- 最大线程数：10
- 队列容量：100
- 拒绝策略：`CallerRunsPolicy`

设计考量：

- 线程池不能无限放大，否则会把压力传导到大模型和第三方图源
- `CallerRunsPolicy` 至少可以起到反压作用，避免任务被静默丢弃

### 4.3 任务状态 tracking

文章任务在数据库里有两层状态：

- `status`：`PENDING / PROCESSING / COMPLETED / FAILED`
- `phase`：
  - `TITLE_GENERATING`
  - `TITLE_SELECTING`
  - `OUTLINE_GENERATING`
  - `OUTLINE_EDITING`
  - `CONTENT_GENERATING`

这个设计的价值：

- `status` 解决“任务成功没成功”
- `phase` 解决“任务当前卡在哪一步”

## 5. 代码窗口

### 5.1 线程池配置

```java
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "articleExecutor")
    public Executor articleExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("article-async-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(60);
        executor.initialize();
        return executor;
    }
}
```

### 5.2 异步执行阶段任务

```java
@Service
public class ArticleAsyncService {

    @Async("articleExecutor")
    public void executePhase1(String taskId, String topic, String style) {
        articleService.updateArticleStatus(taskId, ArticleStatusEnum.PROCESSING, null);
        articleService.updatePhase(taskId, ArticlePhaseEnum.TITLE_GENERATING);

        ArticleState state = new ArticleState();
        state.setTaskId(taskId);
        state.setTopic(topic);
        state.setStyle(style);

        articleAgentOrchestrator.executePhase1_GenerateTitles(state, message -> {
            handleAgentMessage(taskId, message, state);
        });

        articleService.saveTitleOptions(taskId, state.getTitleOptions());
        articleService.updatePhase(taskId, ArticlePhaseEnum.TITLE_SELECTING);
    }
}
```

### 5.4 SSE 实时反馈

```java
public class SseEmitterManager {
    private final Map<String, SseEmitter> emitterMap = new ConcurrentHashMap<>();

    public SseEmitter createEmitter(String taskId) {
        SseEmitter emitter = new SseEmitter(10 * 60 * 1000L);
        emitter.onTimeout(() -> emitterMap.remove(taskId));
        emitter.onCompletion(() -> emitterMap.remove(taskId));
        emitter.onError((e) -> emitterMap.remove(taskId));
        emitterMap.put(taskId, emitter);
        return emitter;
    }

    public void send(String taskId, String message) {
        SseEmitter emitter = emitterMap.get(taskId);
        if (emitter != null) {
            emitter.send(SseEmitter.event().data(message).reconnectTime(3000));
        }
    }
}
```

## 6. 面试官感兴趣的亮点

### 亮点一：接口“受理”和“执行”解耦

怎么回答：

> 我把文章生成拆成了两段：接口只负责受理任务，真正的生成由异步线程池执行。这样接口 RT 会非常稳定，前端也不会因为一次生成请求卡死。

### 亮点二：状态 tracking 做得比较完整

怎么回答：

> 我没有只设计一个任务状态，而是同时设计了 `status + phase` 两层状态。前者表达结果，后者表达执行阶段，这样无论是前端展示还是排障定位，都更清晰。

### 亮点三：SSE 实时回调替代轮询

怎么回答：

> 如果前端轮询，服务端会有很多无效请求；而 SSE 是服务端事件驱动，有进度才推。对这种长耗时、单向通知的场景特别合适。

## 7. 面试常问问题与应对回答

### Q1：为什么用 `@Async`，不用消息队列？

回答思路：

- 当前项目规模下，先用线程池异步足够
- 成本更低，开发更快
- 后续量级上来可演进为 MQ

标准回答：

> 当前项目还处于单体架构阶段，线程池异步能比较低成本地解决问题，而且业务链路需要即时反馈，适合先在应用内异步化。如果后续任务量继续增长，我会把生成任务下沉到 MQ 做削峰和隔离。

### Q2：为什么线程池拒绝策略选 `CallerRunsPolicy`？

标准回答：

> 因为它能形成一种温和的反压机制。当线程池满时，让调用线程执行任务，虽然会让入口请求变慢，但至少不会静默丢任务，对业务来说更安全。

### Q3：如果并发量很高，当前线程池设计有什么风险？

标准回答：

> 风险点主要有两个：第一，线程池队列堆积；第二，下游大模型和图源被打爆。所以高并发场景下我会继续加限流、任务排队和服务降级，而不是盲目扩大线程池。

### Q4：如果 SSE 断开了怎么办？

标准回答：

> SSE 只是进度通知通道，不是结果唯一来源。结果本身已经持久化在 MySQL，所以断开后前端可以重连，或者直接查询任务详情接口补结果。

### Q5：你说“高并发”，具体做了什么？

标准回答：

> 我的理解不是单纯加线程，而是让耗时任务不阻塞主请求线程，同时为前端提供实时状态感知。项目里具体做了线程池异步化、分阶段状态 tracking、SSE 实时回推，以及在配图阶段做了并发执行。

## 8. 面试收尾话术

> 这部分我最核心的价值，是把 AI 场景下的长耗时任务从同步阻塞接口，改造成了异步执行模型，并补齐了状态 tracking 和 SSE 回调机制，让系统在并发能力和用户体验上都更稳。
