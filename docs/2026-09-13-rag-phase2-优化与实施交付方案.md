# RAG Phase 2 优化与实施交付方案

## 1. 交付目标

MVP 已经具备当前项目文档扫描、章节切分、Supabase pgvector 索引、手工文档审核和引用元数据返回能力。Phase 2 的目标不是继续增加一个聊天入口，而是把它提升为可重复同步、可回滚、可评测、可审计的研发知识基础设施。

本阶段完成后，知识库应满足：

- 同步失败不破坏上一版可用知识；
- 重复同步幂等，未变化文档不重复 embedding；
- 精确问题优先命中路径、类名、表名、迁移版本和错误码；
- 所有结果都能追溯到项目、分支、commit、文件和章节；
- 索引状态真实反映待处理、成功、失败和过期；
- 任何用户只能检索当前项目允许公开的有效内容；
- 检索质量有固定问题集和发布门槛，不靠主观体验判断。

## 2. 当前实现差距

| 优先级 | 问题 | 影响 | 处理策略 |
|---|---|---|---|
| P0 | Git 同步是同步 HTTP 请求，按章节串行调用 embedding | 大文档同步超时，前端无法可靠获知进度 | 改为任务化异步同步，返回 taskId，提供状态查询 |
| P0 | 同步前删除旧章节，索引中途失败会造成知识缺失 | 线上可用版本被破坏 | 使用 staging 批次，成功后原子切换 active 批次 |
| P0 | 手工审核先写 ACTIVE，向量写入失败时状态不准确 | 检索结果与数据库治理状态不一致 | 增加 INDEXING、INDEXED、INDEX_FAILED、RETIRED 状态 |
| P0 | 关键词命中分数目前只有 1.0/0.85，且没有字段权重 | 标题、路径、正文无法正确排序 | 引入 token 命中、字段权重、BM25 或数据库全文检索 |
| P0 | 向量命中返回的治理元数据为空 | 引用无法确认版本和来源 | 向量 metadata 必须完整回填，或由 source 反查文档记录 |
| P0 | 当前项目边界依赖固定约定，没有 projectId/visibility 过滤 | 后续扩展时容易发生越权或跨项目污染 | 增加 project_key、visibility、owner/reviewer 过滤，默认拒绝 |
| P1 | Markdown 只按标题切分，没有层级路径和大小上限策略 | 上下文重复，长章节召回质量下降 | 保留 heading hierarchy，按 token 窗口二次切分并设置 overlap |
| P1 | 每次同步都执行 git 命令和全量 embedding | 成本高、耗时长、失败面大 | 以 commit/checksum 做增量同步，embedding 批量化 |
| P1 | 删除/覆盖使用模糊 LIKE 前缀 | 特殊字符可能误删其他 source | 使用精确 source、转义 LIKE，或增加 batch_id 维度 |
| P1 | 缺少索引健康度和失败重试管理 | 只能从日志发现问题 | 增加同步批次、失败原因、重试次数和健康检查 |
| P2 | 代码、SQL、测试还未形成结构化关联 | 只能回答文档问题，不能稳定给出影响范围 | 增加文件/类/方法/迁移/测试轻量实体和关系 |

## 3. 推荐目标架构

```text
Git 文档/代码/测试
        |
        v
扫描与解析器 -- checksum/commit 去重 --> rag_sync_job
        |
        v
staging 文档版本 -- 批量 embedding --> vector_store
        |
        v
校验通过后切换 active_version
        |
        v
关键词召回 + 向量召回 + 元数据过滤 + 重排
        |
        v
引用结果（sourcePath/commit/section/score）
```

MVP 继续复用现有 `RagService`、`RagDocumentStore`、`RagKnowledgeSyncService` 和 Supabase pgvector，不另起数据库或权限系统。新增的是同步任务和版本治理，不是平行基础设施。

## 4. Phase 2 实施分解

### P0-A：同步任务化和版本切换

新增 `rag_sync_job`：

| 字段 | 说明 |
|---|---|
| `id` | 任务 ID |
| `project_key` | 当前项目固定标识 |
| `branch_name` | 同步分支 |
| `commit_sha` | 本次扫描 commit |
| `status` | `QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED` |
| `total_files/processed_files/total_sections/indexed_sections` | 进度 |
| `error_message` | 脱敏后的失败原因 |
| `started_at/finished_at` | 生命周期 |
| `created_by` | 发起人 |

接口：

- `POST /rag/knowledge/sync`：立即返回 `taskId`，重复的相同 commit 返回已有任务；
- `GET /rag/knowledge/sync/{taskId}`：查询进度、失败原因和摘要；
- `POST /rag/knowledge/sync/{taskId}/cancel`：仅允许取消排队任务；
- `POST /rag/knowledge/rebuild`：管理员确认后全量重建。

实施约束：

1. 先扫描并写入 staging 批次，不删除当前 active 批次。
2. 所有文件和章节成功索引后，事务性更新 active batch 指针。
3. 任何失败保留上一版 active 数据，失败任务可重试。
4. 同一项目同时只允许一个 `RUNNING` 任务，使用数据库唯一约束或分布式锁。

### P0-B：索引状态和数据治理

将当前文档状态从简单的 `PENDING_REVIEW/ACTIVE` 扩展为：

```text
PENDING_REVIEW -> APPROVED -> INDEXING -> INDEXED
                                      \-> INDEX_FAILED -> INDEXING
INDEXED -> RETIRED
```

Git 文档可以跳过人工审核，但仍必须经过 `INDEXING` 和 `INDEXED`。`indexed_at` 只有向量写入并校验成功后才能设置；失败必须保存错误摘要，不得伪装成成功。

必须增加的治理字段：

- `project_key`、`visibility`、`owner_id`；
- `sync_job_id`、`batch_id`、`index_version`；
- `index_status`、`index_error`、`retry_count`；
- `content_checksum`、`embedding_model`、`embedding_dimensions`。

### P0-C：混合检索质量

检索分三步：

1. **召回**：关键词召回 `title/sourcePath/sectionPath/text`，向量召回 topK×3；
2. **过滤**：先执行后端 project、visibility、status、branch 和 batch 过滤；
3. **重排**：按归一化分数合并，同一 source/section 去重，并优先当前 commit、标题/路径精确命中和更高向量分数。

推荐初始权重：

```text
finalScore = 0.45 * vectorScore
           + 0.30 * lexicalScore
           + 0.15 * freshnessScore
           + 0.10 * metadataMatchScore
```

权重必须配置化，并通过固定评测集调参。不能继续使用“所有正文命中统一 0.85”的排序方式。

### P0-D：引用和可审计性

每个 `KnowledgeHit` 至少返回：

- `projectKey`、`sourceType`、`domain`、`documentKind`；
- `sourcePath`、`sectionPath`、`commitSha`、`branchName`；
- `documentId`、`chunkId`、`score`、`indexVersion`；
- 可选 `lineStart/lineEnd` 和 Git Web URL。

回答层必须使用引用的 `sourcePath + sectionPath + commitSha`。找不到可靠来源时必须返回“知识库未确认”，不能使用模型常识补齐项目事实。

### P1-A：增量索引和批量 embedding

- 以 `sourcePath + contentChecksum + commitSha` 判断是否变化；
- 未变化章节不重新 embedding；
- embedding 按批次提交，批大小和并发度配置化；
- 失败章节单独重试，不能让整批无限重复；
- 记录 embedding 模型和维度，模型变化时强制新 `indexVersion`；
- 旧版本保留可配置窗口，过期后再清理。

### P1-B：结构化解析

首批支持：

- Markdown：标题层级、代码块、表格、列表、source line；
- Java：package、class、method、注解和文件路径；
- TypeScript/Vue：组件、composable、API 方法和路由；
- SQL：迁移版本、表、字段和索引；
- 测试：测试类、测试方法、覆盖的接口/场景。

解析器必须失败可降级：解析失败时仍可按文件文本索引，并记录 `parser_status=FALLBACK`。

### P2：研发助手工作流

在知识库稳定后接入：

```text
grill me -> 只读盘点 -> 生成 write plan -> 人工确认
        -> 实施 -> 测试证据 -> 代码/文档评审 -> 知识库更新
```

第一版只允许检索、引用、提问和生成计划；禁止自动改 Git、审批知识、创建提交和执行生产命令。计划必须区分 `PROPOSED`、`IMPLEMENTED`、`VERIFIED`，测试没有证据时不能标记完成。

## 5. 文件级交付清单

### 后端

- `RagKnowledgeSyncService`：拆分扫描、解析、任务编排和批次切换；
- `RagKnowledgeBaseService`：实现召回融合、字段权重、版本和权限过滤；
- `RagDocumentStore`：增加版本/索引状态更新、精确删除和失败重试；
- `RagService`：支持 batch metadata、批量 embedding 和索引版本；
- `RagController`：新增同步任务状态、重试和健康检查接口；
- 新增 `RagSyncJob`、Mapper、Service、VO 和数据库迁移；
- 新增 `RagKnowledgeMetrics` 或复用现有统计入口记录检索/索引指标。

### 前端

- `KnowledgePage.vue`：同步任务进度、失败原因、重试、当前 active commit 展示；
- 增加领域、状态、来源、分支和 commit 过滤；
- 上传审核增加审核意见、索引状态和失败恢复按钮；
- 检索结果展示完整引用并支持复制 source path/commit；
- 不能把长同步伪装成普通 loading，应显示任务状态和可恢复错误。

### 文档

- `docs/knowledge/index.md`：补充 owner、状态、复核日期和来源约定；
- 四类文档增加 front matter：`project/domain/kind/status/owner/reviewedAt/source`；
- 新增 ADR：同步任务化、版本切换、混合排序、embedding 模型升级；
- 固化 40 条评测问题：规范、业务、开发、测试各 10 条。

## 6. 专业测试矩阵

### 单元测试

- Markdown 层级路径、无标题文档、超长章节和代码块切分；
- checksum 相同跳过 embedding，checksum 变化只重建变化章节；
- 空查询、topK 边界、关键词字段权重和重复 source 去重；
- 状态机非法迁移、重试次数、失败原因脱敏；
- Git 命令超时、非 Git 目录、分支不匹配和路径穿越。

### 集成测试

- staging 批次失败后 active 旧版本仍可检索；
- 全部成功后只返回新 batch；
- 同一 commit 重复同步幂等；
- 同时触发两个同步任务只允许一个运行；
- pgvector 不可用时健康状态为降级，业务主流程不被阻塞；
- 普通用户、管理员、未审核文档、其他 project 的过滤结果符合 fail-closed；
- 手工上传、审核、索引失败、重试、删除的完整状态流。

### 评测测试

固定 40 条问题，每条记录：`goldSource`、必答要点、禁答内容、适用 commit。发布门槛：

| 指标 | MVP 基线 | Phase 2 门槛 |
|---|---:|---:|
| Recall@5 | 80% | >= 90% |
| MRR@5 | 0.70 | >= 0.82 |
| 当前版本优先率 | 90% | >= 98% |
| 引用覆盖率 | 95% | 100% |
| 权限越界 | 0 次 | 0 次 |
| 未确认问题正确拒答 | 未统计 | >= 95% |

### 质量门

```text
mvn -q -DskipTests compile
mvn -q -Dtest='*Rag*Test' test
cd frontend
npm run type-check
npm run build-only
npm run test:skill
```

真实联调必须记录：后端、前端、MySQL、Redis、Supabase pgvector、embedding API、登录 Session、同步 commit、任务 ID、结果摘要和失败证据。不能以 mock embedding 结果替代真实联调结论。

## 7. 交付顺序与完成定义

### 第一个垂直切片：同步任务化

交付迁移、任务表、状态 API、后台进度页、并发锁和失败保留旧版本。完成标准是能启动任务、轮询状态、失败可见、旧索引仍可检索。

### 第二个垂直切片：版本安全切换

交付 staging batch、active 指针、重试和幂等。完成标准是模拟 embedding 中途失败，线上仍返回上一个完整版本。

### 第三个垂直切片：混合检索和引用

交付字段权重、过滤、完整引用和 40 条评测集。完成标准是达到 Phase 2 门槛，且没有权限越界。

### 第四个垂直切片：后台治理体验

交付审核意见、状态筛选、失败重试、健康检查和文档复核信息。完成标准是管理员不依赖日志即可定位同步和索引问题。

### 总完成定义

- 代码、迁移、API、前端和测试全部落地；
- 失败、重试、回滚、权限和幂等均有自动化证据；
- 40 条评测问题达到门槛；
- 交付文档记录实际命令、环境、commit 和已知限制；
- `git diff --check` 通过，提交不含密钥、Cookie、临时日志和生成物。

## 8. 暂不实现

- 不让模型直接写 Git、创建 PR、审批知识或执行生产迁移；
- 不把全部代码一次性转成无结构向量；
- 不在没有评测集的情况下引入复杂 reranker；
- 不为了 RAG 新建第二套用户、权限或项目系统；
- 不把后台手工上传内容直接视为 Git 权威事实源。

## 9. 推荐下一步

下一轮建议只实施第一个垂直切片：**同步任务化 + 失败保留旧版本**。这是当前收益最高、风险最明确的改造；完成并通过真实 Supabase 联调后，再实施混合检索评分和结构化代码解析。
