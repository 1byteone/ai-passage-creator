# 灵犀写作｜策略模式与扩展能力项目复盘

## 1. 这一项职责在项目中的定位

- 图文创作平台的一个难点是：图片来源不止一种。
- 真实图库、AI 生图、Mermaid 图表、SVG 示意图、表情包、Icon 图标，这些能力的输入、输出和失败模式都不一样。
- 我负责把这些差异能力抽象成统一的图片策略体系，做到可插拔、可降级、可统一返回。

一句话面试表达：

> 我基于策略模式抽象了多源配图能力，把 Pexels、Mermaid、SVG、Emoji、Iconify 等图源统一接入，并通过服务可用性检测、失败降级和统一结果封装（含 COS 上传），提升了系统的扩展性和容错性。同时设计了基于 imageSource 分组的并行生成策略，兼顾效率与限流防护。

---

## 2. 功能描述

### 业务问题

- 不同文章适合不同图源：
  - 科普类适合 Mermaid / SVG
  - 情绪类可能适合表情包
  - 写实类适合 Pexels
  - 创意表达适合 AI 生图

### 我的目标

- 把图源差异对上层业务透明化
- 新增一个图源时尽量不改主流程
- 某个图源失败时能自动降级
- 最终都输出统一的图片结果对象
- 同类型图源串行执行避免 API 限流，不同类型并行执行提升效率

---

## 3. 业务流程

### 主流程

1. 正文生成完成后，`ImageAnalyzerAgent` 分析每个插图位置需要什么图源，生成 `ImageRequirement` 列表（含 position、imageSource、keywords、prompt）
2. 系统对 `ImageRequirement` 按 `imageSource` 分组，不同类型并行执行，同类型串行执行
3. 每个图源实现通过策略接口 `ImageSearchService` 执行检索/生成
4. 结果统一转成 `ImageData`（支持 bytes、URL、data URL 三种形态）
5. 上传到 COS，得到稳定访问 URL
6. 如果失败，自动走 fallback 图
7. 统一封装成 `ImageResult` 供后续图文合成使用

### 并行策略细节

- 按 `imageSource` 分组（如 PEXELS、MERMAID、ICONIFY）
- 每组分配给一个 `CompletableFuture` 并行执行
- 同一组内串行执行，防止对同一 API 源造成并发压力
- 使用 `CopyOnWriteArrayList` 收集结果保证线程安全
- `CompletableFuture.allOf().join()` 等待全部完成
- 最终按 position 排序输出

## 4. 核心设计

### 4.1 策略模式怎么落地

- 抽象接口：`ImageSearchService`
- 每个图源实现自己的 `searchImage / getImageData / getMethod / getFallbackImage / isAvailable`
- 运行时由 `ImageServiceStrategy` 根据 `ImageMethodEnum` 进行分发
- 所有实现类通过 Spring 自动注入到 `List<ImageSearchService>`，`@PostConstruct` 时注册到 `EnumMap`

这样做的好处：

- 新图源接入只需要新增实现类
- 上层逻辑不关心底层细节
- 容易做可用性检测和统一上传

### 4.2 数据流转链

```
ArticleState.ImageRequirement
  → ImageRequest (keywords/prompt/position/type)
    → ImageSearchService.getImageData(request)
      → ImageData (bytes/URL/dataURL)
        → CosService.uploadImageData(imageData, folder)
          → ArticleState.ImageResult (cosUrl/method/position)
```

### 4.3 为什么不写成 if-else

- 少量图源时，if-else 看起来很快
- 但图源越多，条件分支越难维护
- 新增一个图源会修改原有逻辑，违反开闭原则

### 4.4 Agent Tool 封装

`ImageGenerationTool` 用 `@Tool` 注解将 `ImageServiceStrategy` 包装为 Spring AI Agent 可调用的工具，支持 Agent 编排场景下的图片生成。同时提供 `generateImageDirect` 方法供 `ParallelImageGenerator` 内部直接调用，绕过 Agent 层。

### 4.5 权限与策略结合

当前项目对图源做了用户分层控制：

- 普通用户默认允许：
  - `PEXELS`
  - `MERMAID`
  - `ICONIFY`
  - `EMOJI_PACK`
- VIP 用户可以使用更高级能力：
  - `NANO_BANANA`（AI 生图，如用 Gemini 原生图片生成能力）
  - `SVG_DIAGRAM`

这说明策略体系不只是技术抽象，也和商业化能力绑定了。

## 5. 代码窗口

### 5.1 图片策略接口

```java
public interface ImageSearchService {

    default String getImage(ImageRequest request) {
        String param = request.getEffectiveParam(getMethod().isAiGenerated());
        return searchImage(param);
    }

    default ImageData getImageData(ImageRequest request) {
        String url = getImage(request);
        return ImageData.fromUrl(url);
    }

    String searchImage(String keywords);

    ImageMethodEnum getMethod();

    String getFallbackImage(int position);

    default boolean isAvailable() {
        return true;
    }
}
```

### 5.2 策略注册与分发

```java
@Service
public class ImageServiceStrategy {

    @Resource
    private List<ImageSearchService> imageSearchServices;

    @Resource
    private CosService cosService;

    private final Map<ImageMethodEnum, ImageSearchService> serviceMap = new EnumMap<>(ImageMethodEnum.class);

    @PostConstruct
    public void init() {
        for (ImageSearchService service : imageSearchServices) {
            serviceMap.put(service.getMethod(), service);
        }
    }

    public ImageResult getImageAndUpload(String imageSource, ImageRequest request) {
        ImageMethodEnum method = resolveMethod(imageSource);
        ImageSearchService service = serviceMap.get(method);

        if (service == null || !service.isAvailable()) {
            return handleFallbackWithUpload(request.getPosition());
        }

        try {
            ImageData imageData = service.getImageData(request);

            if (imageData == null || !imageData.isValid()) {
                return handleFallbackWithUpload(request.getPosition());
            }

            String folder = getFolderForMethod(method);
            String cosUrl = cosService.uploadImageData(imageData, folder);

            if (cosUrl != null && !cosUrl.isEmpty()) {
                return new ImageResult(cosUrl, method);
            } else {
                return handleFallbackWithUpload(request.getPosition());
            }
        } catch (Exception e) {
            return handleFallbackWithUpload(request.getPosition());
        }
    }
}
```

### 5.3 并行图片生成（按类型分组）

```java
private List<ArticleState.ImageResult> executeParallel(
        Map<String, List<ArticleState.ImageRequirement>> groupedBySource,
        Consumer<String> streamHandler) {

    CopyOnWriteArrayList<ArticleState.ImageResult> allImages = new CopyOnWriteArrayList<>();

    List<CompletableFuture<Void>> futures = groupedBySource.entrySet().stream()
            .map(entry -> CompletableFuture.runAsync(() -> {
                String imageSource = entry.getKey();
                List<ArticleState.ImageRequirement> requirements = entry.getValue();

                // 同一类型内部串行执行（防止 API 限流）
                for (ArticleState.ImageRequirement req : requirements) {
                    ImageGenerationTool.ImageGenerationResult result =
                            imageGenerationTool.generateImageDirect(
                                    req.getImageSource(), req.getKeywords(),
                                    req.getPrompt(), req.getPosition(),
                                    req.getType(), req.getSectionTitle(),
                                    req.getPlaceholderId());
                    // 收集结果...
                }
            }))
            .toList();

    CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

    // 按 position 排序
    allImages.sort(Comparator.comparing(ArticleState.ImageResult::getPosition));
    return new ArrayList<>(allImages);
}
```

### 5.4 用户权限控制图源

```java
private void validateImageMethods(List<String> enabledImageMethods, User loginUser) {
    if (enabledImageMethods == null || enabledImageMethods.isEmpty()) {
        return;
    }
    if (isVipOrAdmin(loginUser)) {
        return;
    }
    for (String method : enabledImageMethods) {
        if ("NANO_BANANA".equals(method) || "SVG_DIAGRAM".equals(method)) {
            throw new BusinessException(ErrorCode.NO_AUTH_ERROR, "高级配图功能仅限 VIP");
        }
    }
}
```

### 5.5 普通用户默认配图方式

```java
private List<String> processImageMethods(List<String> enabledImageMethods, User loginUser) {
    if (enabledImageMethods != null && !enabledImageMethods.isEmpty()) {
        return enabledImageMethods;
    }
    if (isVipOrAdmin(loginUser)) {
        return null; // null 表示支持所有方式
    }
    // 普通用户：只开放低成本能力
    return List.of(
        ImageMethodEnum.PEXELS.getValue(),
        ImageMethodEnum.MERMAID.getValue(),
        ImageMethodEnum.ICONIFY.getValue(),
        ImageMethodEnum.EMOJI_PACK.getValue()
    );
}
```

### 5.6 失败降级

```java
private ImageResult handleFallbackWithUpload(Integer position) {
    int pos = position != null ? position : 1;
    String fallbackUrl = getFallbackImage(pos);
    ImageData fallbackData = ImageData.fromUrl(fallbackUrl);
    String cosUrl = cosService.uploadImageData(fallbackData, "fallback");
    String finalUrl = (cosUrl != null && !cosUrl.isEmpty()) ? cosUrl : fallbackUrl;
    return new ImageResult(finalUrl, ImageMethodEnum.getFallbackMethod());
}
```

## 7. 面试官感兴趣的亮点

### 亮点一：策略模式不是为模式而模式

怎么回答：

> 这个项目的图源类型天然多样，而且未来还会继续增加，所以我用策略模式不是为了秀设计模式，而是为了让新增图源时对主流程零侵入。

### 亮点二：扩展能力和商业化结合

怎么回答：

> 我把图源能力和用户等级做了结合。对普通用户开放低成本能力，对 VIP 开放 AI 生图和更高级图表能力，这样技术设计直接服务于产品分层。

### 亮点三：并行执行 + 同类型串行保护

怎么回答：

> 因为配图数量可能很多，但不同图源之间不存在耦合，所以我按 imageSource 分组做了并行生成。同时同类图源内部串行执行，避免并发请求打爆第三方 API 造成限流。

### 亮点四：失败降级提升稳定性

怎么回答：

> 我没有把第三方图源当成一定可用，而是在策略层就考虑了服务不可用和回退逻辑。而且图源接口返回的可能是 bytes 或 data URL，我会先转成 ImageData，再上传 COS 统一为稳定 URL，这样即使某个图源挂掉，主流程也不至于失败。

## 8. 面试常问问题与应对回答

### Q1：你为什么选择策略模式？

标准回答：

> 因为不同图源的调用方式差异很大，但上层业务只关心"给我一张图"。策略模式能把差异封装到底层实现里，让主流程保持稳定。

### Q2：如果再新增一个新的图源，比如 Unsplash，你要改哪些地方？

标准回答：

> 我只需要新增一个 `ImageSearchService` 的实现类，并在 `ImageMethodEnum` 中增加一个枚举值。因为策略注册是自动扫描 + 映射初始化，所以主流程基本不用动，仅在 `ImageServiceStrategy` 的 `getFolderForMethod` switch 中加一个 case。

### Q3：为什么要统一上传 COS？

标准回答：

> 不同图源返回的 URL 生命周期和可用性不一致，有的返回字节数据，有的返回 data URL。统一上传 COS 后，对前端暴露的就是稳定 URL，也更方便做权限控制、访问加速和统一渲染。

### Q4：降级逻辑为什么要放在策略层，而不是 Controller 层？

标准回答：

> 因为降级本质上属于能力调用链路的一部分，不应该泄露给上层业务。放在策略层可以让上层只感知"拿到可用结果"，而不必知道中间做过回退。

### Q5：你提到的"并行图片生成"具体怎么做？

标准回答：

> 我收到图片需求列表后按 imageSource 分组，每组开一个 CompletableFuture 并行执行。同组内部串行执行以防止 API 限流。结果用 CopyOnWriteArrayList 收集，最后 allOf().join() 等待结束，再按 position 排序输出。

### Q6：如果图源很多，策略模式会不会也变复杂？

标准回答：

> 会，但这种复杂度是可控复杂度。因为每个实现类都被隔离在自己的边界里，复杂度不会传染到主流程。相比巨型 if-else，这种复杂度更容易维护。

## 9. 面试收尾话术

> 这部分我最看重的是"可扩展性"。我把多源图片能力抽象成统一策略，不仅解决了当前图源接入问题，也把后续新增能力、并行生成、故障降级和会员分层都纳入了同一套设计里。同时通过按 imageSource 分组的并行策略，兼顾了生成效率和 API 限流防护。
