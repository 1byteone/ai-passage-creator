# RAG 研发知识库调研与交付方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 项目 | ai-passage-creator |
| 调研日期 | 2026-09-12 |
| 目标分支 | `dev_rag`，基于 `dev` |
| 调研目标 | 判断是否适合建设研发知识库，给出可执行的文档体系、AI 协作流程、技术方案和验收标准 |
| 结论级别 | 建议建设，先做研发知识库 MVP，再扩展为可检索的代码/文档助手 |

## 2. 执行摘要

### 2.1 结论

项目适合接入 RAG 知识库，但目标应定义为“研发知识系统”，而不是单纯的向量数据库。原因有三点：

1. 项目已有较成熟的 RAG 基础设施：Spring AI `VectorStore` 抽象、Supabase pgvector 主存储、内存降级、DashScope embedding、文档入库、文章/Skill 自动索引、引用溯源和前端知识库页面。
2. 项目已有较强的工作流和测试基础：Skill 引擎、HITL、SSE、阶段计划、设计文档、测试文档和 `AGENTS.md`/`CLAUDE.md` 规则，天然适合“先澄清、再计划、后实现”的 AI 协作。
3. 当前缺口不在“能不能搜”，而在“搜到的内容是否正确、是否属于当前版本、是否有权限、是否能被验证”。研发知识库必须同时管理事实、决策、流程、测试证据和代码变更关系。

### 2.2 推荐边界

第一阶段只建设“项目研发知识库”，覆盖：

- 技术规范：技术栈、目录边界、封装组件、约定、禁止事项。
- 业务知识：模块、角色、状态机、业务规则、权限、正常/异常流程。
- 开发知识：任务拆分、依赖顺序、接口契约、数据库迁移、联调方式、回滚策略。
- 测试知识：测试入口、测试数据、正常流、异常流、验收标准、已知缺陷和证据。
- 决策记录：为什么采用某个方案、被否决的方案、影响和后续复审条件。

暂不把“自动修改生产代码”“完全依赖 LLM 生成测试”“把所有日志和临时文件入库”作为 MVP 目标。

### 2.3 最重要的原则

> 文档是事实源，RAG 是定位器，测试是裁判，人工是最终授权者。

RAG 不应替代代码、数据库迁移和测试结果。它的职责是快速找到相关上下文，并要求回答带来源、带版本、带不确定性说明。

## 3. 对当前项目的盘点

### 3.1 已有能力

当前代码已经具备以下可复用能力：

| 能力 | 现状 | 对研发知识库的价值 |
|---|---|---|
| 向量库 | `RagVectorStoreConfig` 支持 Supabase pgvector，开发环境可退回 `SimpleVectorStore` | 可复用存储和测试替身 |
| 分块和 embedding | `RagService` 使用 `TokenTextSplitter` 和 DashScope embedding | 可作为文档索引基线，但需要按 Markdown 结构优化 |
| 检索过滤 | 按 `type`、`userId` 过滤，并对分数做归一化 | 可扩展为 project、domain、branch、visibility、status 过滤 |
| 文档入库 | `RagDocument`、`RagDocumentStore`、`RagController`、管理页已存在 | 可演进为 Git 同步和文档生命周期管理 |
| 业务索引 | 文章、Skill 输出自动索引 | 说明项目已经有异步索引模式和失败不阻断主流程的经验 |
| 引用溯源 | `RagReference` 保存阶段、来源、类型、分数 | 可扩展为回答引用、版本和检索评测证据 |
| 安全防护 | 文档入库有 HTML 清洗和部分提示注入过滤；检索有熔断 | 可作为安全基线，但不能替代权限和提示注入隔离 |
| AI 工作流 | Skill、HITL、SSE、阶段状态和检查点 | 可承载“提问、计划、执行、验证”的任务状态机 |
| 文档资产 | `PROJECT_ARCHITECTURE.md`、`CLAUDE.md`、`AGENTS.md`、设计/计划文档、RAG 资料脚本已存在 | 已有事实材料，但组织方式和元数据还不统一 |

### 3.2 当前实现的关键限制

当前 `RagDocument` 主要包含 `title/source/text/userId/createTime/updateTime`，向量 metadata 主要包含 `type/title/source`。对于研发知识库，至少还需要：

- `projectId`：避免多项目共用索引时串库。
- `domain`：`standard`、`business`、`development`、`testing`、`decision`。
- `documentKind`：规范、模块说明、流程、ADR、接口契约、测试用例、运行手册等。
- `status`：draft、active、deprecated、superseded、archived。
- `version` / `commitSha` / `branch`：回答“哪一版代码/文档”的必要条件。
- `owner` / `reviewer` / `reviewedAt`：责任人和复核周期。
- `visibility` / `workspaceId`：权限隔离，不能只依赖前端过滤。
- `sourcePath` / `sourceUrl` / `lineStart` / `lineEnd`：可回到 Git 文件或代码位置。
- `checksum` / `indexedAt` / `parserVersion` / `embeddingModel`：幂等更新和重建索引所需。
- `parentDocumentId` / `sectionPath` / `headingPath`：按章节追溯上下文。

另一个重要限制是：当前检索主要是向量相似度检索。对于类名、接口名、表名、错误码、迁移版本号和配置键，精确关键词往往比语义相似更可靠，因此研发知识库应使用混合检索或至少增加关键词召回。

## 4. 为什么适合，但不能直接照搬业务 RAG

### 4.1 业务 RAG 和研发 RAG 的区别

| 维度 | 现有文章创作 RAG | 研发知识库 RAG |
|---|---|---|
| 主要问题 | 找相似文章、参考内容 | 找当前版本的规则、代码关系、测试证据 |
| 允许的错误 | 结果风格不完全匹配 | 错版本、错权限、错接口可能直接导致缺陷 |
| 文档粒度 | 文章段落 | Markdown 章节、Java 类/方法、SQL 迁移、测试方法 |
| 主要检索 | 语义相似 | 语义 + 关键词 + 元数据 + 依赖关系 |
| 主要过滤 | 用户、文章类型 | 项目、分支、版本、领域、状态、权限 |
| 主要输出 | 参考内容 | 结论、来源、版本、影响文件、测试建议、未确认项 |
| 成功标准 | 内容相关、能生成 | 可追溯、可验证、不过时、没有越权和编造 |

### 4.2 是否需要 GraphRAG

暂不建议一开始引入知识图谱或 GraphRAG。当前项目规模和个人维护能力更适合：

1. 先用结构化 Markdown + metadata 做好事实源和过滤。
2. 再从 Git、Java、SQL、Vue 中提取轻量关系：模块依赖、Controller-Service-Mapper、表-迁移、页面-接口、测试-功能。
3. 当出现跨文件、多跳问题明显成为瓶颈时，再引入图存储或关系增强检索。

也就是说，先做“metadata-first、hybrid retrieval”，而不是先做“graph-first”。图结构适合回答“谁依赖谁”“改这个表会影响哪些接口”，但前提是实体和关系的提取质量足够高。

## 5. 推荐的四类文档体系

四类分类合理，但建议增加一个横向的“决策与证据层”。四类文档是内容域，决策和证据是治理属性。

### 5.1 项目规范文档 `standard`

回答“这个项目应该怎么做”。建议包含：

- 项目定位、边界和非目标。
- 技术栈与版本矩阵。
- 目录职责和依赖方向。
- 已封装组件：输入、输出、异常、线程模型、使用示例、禁止用法。
- API、DTO、数据库、缓存、Session、SSE、日志和错误码约定。
- 安全基线：权限、IDOR、SSRF、提示注入、密钥、敏感数据、对象存储。
- 前端组件、请求封装、状态管理和 UI 约定。
- 开发质量门：后端测试、前端 type-check/build、Playwright、迁移验证。

文档必须区分“强制规则”和“建议规则”，否则模型会把个人偏好当成硬约束。

### 5.2 业务文档 `business`

回答“用户和系统为什么这样运行”。每个模块至少按以下模板记录：

- 角色和权限。
- 前置条件。
- 输入、输出和状态。
- 正常事件流。
- 异常事件流和恢复方式。
- 不变量和限制。
- 与其他模块的衔接。
- 关联页面、接口、表、配置和测试。
- 尚未确认的产品决策。

当前项目建议优先整理文章创作、Skill 执行/HITL、RAG 文档库、审批/发布、漫画手帐、英语训练、数据分析七个模块。

### 5.3 开发文档 `development`

回答“实现这个需求先做什么、后做什么、如何衔接”。推荐每个功能有一份短计划：

- 背景和目标。
- 范围、非范围和风险。
- 现状调查和复用点。
- 数据库/接口/后端/前端/测试的依赖顺序。
- 具体文件和修改边界。
- 迁移、兼容、回滚策略。
- 开发任务和完成定义。
- 需要用户确认的问题。

开发计划是 AI 执行的输入，但不是事实源。计划完成后应由代码、测试和评审结果反向更新知识库。

### 5.4 测试文档 `testing`

回答“怎样证明它工作，以及失败时怎样定位”。建议每个功能记录：

- 测试范围和不测试范围。
- 环境、配置、账号类型和可重复测试数据。
- 单元、集成、接口、UI、联调和回归入口。
- 正常事件流。
- 异常事件流：空输入、非法输入、未授权、重复提交、超时、依赖失败、并发、数据不存在、迁移失败。
- 预期结果、实际结果和证据路径。
- 缺陷、阻塞、已修复、待回归状态。
- 运行命令和通过门槛。

测试文档不能只写“已测试”。必须关联测试方法、断言和证据，否则无法被 AI 或人复核。

### 5.5 决策与证据层 `decision` / `evidence`

建议采用 ADR 记录架构性决策，每条只描述一个决策：

- 状态：proposed、accepted、superseded、deprecated。
- 背景和约束。
- 备选方案。
- 选择及理由。
- 代价、风险和后果。
- 影响的模块和文件。
- 复审触发条件。

证据包括测试报告、构建日志、接口样例、截图、性能数据和真实联调记录。证据应带时间、版本和环境，不能只保留一句结论。

每个文档开头使用统一 front matter，至少包括：

kind: workflow
status: active
owner: project-owner
reviewer: project-owner
version: 1

规则：代码和迁移发生变化时，相关文档必须在同一个提交或同一个变更任务中更新；文档没有来源路径或测试关联时，默认只能作为草稿，不能作为强约束上下文。

## 7. 推荐技术方案

### 7.1 总体结构

```text
Git 文档 + 代码 + SQL + 测试 + ADR
                 |
      解析、切分、元数据提取、脱敏
                 |
  文档登记表 + pgvector 向量索引 + 关键词索引
                 |
         权限过滤 + 混合召回 + 重排
                 |
       引用化上下文 + 版本/来源/置信度
                 |
       问答 / 计划审查 / 实现辅助 / 测试建议
```

### 7.2 检索策略

建议分三层：

1. **硬过滤**：`projectId`、`workspaceId`、权限、`status=active`、目标分支/版本。
2. **混合召回**：向量检索召回语义相关内容；关键词检索保证类名、表名、错误码、路径和配置键命中。
3. **重排和去重**：按文档状态、来源新鲜度、章节完整性、测试关联和相似度重排；同一文档的相邻 chunk 合并，避免上下文碎片化。

回答必须输出：结论、依据、来源文件/章节、版本或 commit、适用范围、未确认项。没有足够证据时应回答“知识库没有确认”，而不是补全猜测。

### 7.3 索引策略

- Markdown：按标题层级切分，保留 `headingPath`，不要简单按固定字符截断。
- Java/TypeScript：按类、方法、接口和注释切分，保存文件路径与行号。
- SQL：按迁移文件和 DDL 语句切分，保存 migration version 和表名。
- 测试：按测试类/方法切分，保存测试类型、覆盖场景和运行命令。
- 计划/ADR：整条决策尽量保持在同一个 chunk，避免只检索到结论而丢失理由。

embedding 模型、维度和解析器版本必须写入索引元数据。更换 embedding 维度或切分策略时，应建立新索引版本并进行离线评测，不能原地混用。

### 7.4 事实源和手工上传策略

本项目知识库只服务当前项目，`projectId` 仍保留为元数据字段，但固定为当前项目标识，暂不建设多项目租户能力。

Git 是唯一正式事实源。`docs/knowledge/`、代码、SQL、测试和 ADR 进入 Git 后，才能成为 `active` 的权威知识。管理后台和手工上传保留，定位为录入和补充渠道：

1. 手工上传先创建 `draft` 或 `pending_review` 文档，默认不参与普通问答。
2. 文档必须补充领域、类型、来源、owner、适用版本和关联路径。
3. 项目负责人审核后才可标记为 `active`；审核记录和时间必须保存。
4. 审核通过的内容应回写到 `docs/knowledge/` 并提交 Git，后台记录 Git 路径和 commit。
5. Git 中的文档发生变更后，旧版本标记为 `superseded`，重新索引新版本。

这样既保留了后台录入的便利，又避免后台数据库里出现一份无法评审、无法回滚、无法追踪的“第二套真相”。第一阶段只读意味着 AI 可以检索、回答和生成计划，但不能直接修改 Git、审批文档或执行迁移。

### 7.5 复用与改造清单

可复用：

- `RagVectorStoreConfig` 的 pgvector/内存双实现。
- `RagService` 的异步索引、失败熔断、分数归一化和基础清洗。
- `RagDocumentStore` 的文档登记与幂等更新思路。
- `RagReferenceStore` 的引用持久化模型。
- Spring AI 的 `VectorStore`、`SearchRequest` 和 metadata filter。

必须改造：

- 将共享文档从“单一 source + text”升级为“文档登记 + 文档版本 + chunk 索引”。
- 增加 project/domain/kind/status/branch/commit/owner/visibility/sourcePath 等元数据。
- 增加 Git 同步或本地目录扫描，人工上传作为补充入口。
- 增加关键词召回和混合排序。
- 增加回答引用、检索日志和离线评测数据集。
- 将提示注入防护从“文本清洗”升级为“上下文角色隔离”：检索内容永远是数据，不能成为系统指令；输出只允许基于引用回答。

不建议现在做：

- 为了 RAG 另起一套数据库和权限系统。
- 一次性给所有代码自动生成大量没有来源的说明。
- 让模型自动修改规范文档或直接执行数据库迁移。
- 用单次人工主观体验代替检索评测。

## 8. `grill me` + `write plan` 工作流建议

你设想的流程是合理的，但“疯狂提问”必须有边界，否则会变成低收益的反复确认。建议固定为六个阶段。

### 阶段 A：任务澄清

AI 只做调查和提问，不改业务代码。问题分为：

- 目标：解决谁的什么问题，成功指标是什么。
- 范围：包含什么，不包含什么。
- 现状：现有模块、接口、表、组件和可复用实现。
- 约束：兼容性、性能、安全、成本、上线方式。
- 流程：正常流、异常流、权限和恢复。
- 数据：输入、输出、生命周期、幂等和脱敏。
- 验收：如何证明完成，哪些情况必须失败。

结束条件不是“问得越多越好”，而是所有 P0 未决问题有答案，其余问题被明确标记为“待确认”。

### 阶段 B：生成并审阅计划

`write plan` 生成 Markdown 计划，必须包含：

- 背景、目标、非目标。
- 影响范围和风险。
- 现有代码证据。
- 数据库、接口、后端、前端、测试的任务顺序。
- 文件级修改清单。
- 失败处理、兼容和回滚。
- 测试命令、验收标准和完成定义。

计划必须由用户确认后才进入实现。计划是“本次任务的执行契约”，不是永久规范。

### 阶段 C：实现

AI 每次只执行一个可验证的垂直切片，例如“迁移 + Mapper + Service + 单元测试”，完成后更新任务状态。不能为了完成一个功能顺手重构无关模块。

### 阶段 D：验证

先运行计划中定义的测试，再运行项目质量门。失败时记录原因、修复动作和剩余风险。测试文档应更新为事实，不应由 AI 直接把“计划通过”写成“已通过”。

### 阶段 E：评审

至少检查：需求符合度、权限、数据隔离、异常流、并发/幂等、迁移、日志敏感信息、测试真实性、文档是否同步。

### 阶段 F：沉淀

将稳定事实更新到四类知识文档；将架构取舍写成 ADR；将一次性任务计划和证据归档。下一次新任务先读取规则、相关业务文档、最近 ADR、相关测试和当前计划，而不是把全库全文塞进上下文。

## 9. 分阶段实施计划

### Phase 0：知识库清点和基线，1-2 天

交付：目录、front matter 模板、文档索引、文档清单、重复/过期/待确认清单。

验收：四类文档各有至少一份真实文档；每份文档有 owner、状态、来源和复核日期；不修改业务代码。

### Phase 1：最小研发知识库，3-5 天

交付：Git 文档扫描、Markdown 分块、元数据登记、pgvector 索引、按项目/领域/状态过滤、引用输出。

建议首批内容：`AGENTS.md`、`CLAUDE.md`、`PROJECT_ARCHITECTURE.md`、`CONTRIBUTING.md`、`DEPLOYMENT.md`、核心 RAG 设计/计划、核心模块测试说明。

验收：20 个固定问题中，相关文档 Top-5 召回率达到 80% 以上；回答 100% 带来源；权限越界问题 0 次。

### Phase 2：混合检索和版本治理，3-5 天

交付：关键词召回、版本/commit/branch、active/superseded、增量索引、删除和重建索引、索引健康检查。

验收：类名、路径、表名、迁移版本、错误码等精确问题不依赖语义相似度；旧文档不会覆盖当前文档；重复同步幂等。

### Phase 3：代码和测试关联，5-10 天

交付：Java/TypeScript/SQL/测试结构化解析；文件/类/方法/表/测试之间的轻量关系；“改动影响范围”和“相关测试建议”。

验收：选定 10 个功能，能从业务文档定位到接口、实现、表和测试；变更文件能给出候选回归测试清单。

### Phase 4：AI 研发助手，5-10 天

交付：`grill` 任务澄清、`plan` 计划生成、计划审阅、实现前检查、测试结果回写、来源引用和未确认项管理。第一版仅允许只读检索、只读分析和计划生成，不允许直接修改 Git、审批文档、创建提交或执行生产操作。

验收：新功能任务可以从澄清进入计划；计划未确认时不改代码；完成后能生成变更摘要、测试摘要和文档更新清单。

### Phase 5：评测和持续治理，持续进行

交付：固定问答集、检索指标、引用正确性、过期文档告警、索引失败告警、人工反馈闭环。

验收：每次 embedding、切分、重排或 prompt 变更都有离线回归；指标下降阻止发布或明确人工批准。

## 10. RAG 评测与测试标准

### 10.1 检索层

- Recall@K：正确来源是否出现在前 K 个结果。
- Precision@K：前 K 个结果中真正相关的比例。
- MRR / nDCG：正确结果出现的位置和排序质量。
- Freshness：当前版本文档优先于过期文档。
- Filter accuracy：项目、权限、分支、领域过滤是否正确。
- Citation coverage：回答需要引用时是否都给出来源。

### 10.2 生成层

- Faithfulness：回答是否能被引用内容支持。
- Completeness：是否遗漏关键前置条件、异常流和限制。
- Abstention：知识库没有答案时是否明确拒答或请求澄清。
- Version correctness：是否引用了错误分支或过期文档。
- Instruction isolation：检索文档中的指令是否不会覆盖系统约束。

### 10.3 固定测试集建议

建立至少 40 条问题，覆盖：

- 10 条规范问题：技术栈、组件用法、禁止事项。
- 10 条业务问题：流程、权限、状态、异常恢复。
- 10 条开发问题：改哪些文件、先后顺序、接口和迁移。
- 10 条测试问题：测试命令、正常流、异常流、回归范围。

每条问题记录 gold source、允许的答案要点、必须避免的错误和版本。评测数据不能只由模型生成，至少由人工审核一遍。

### 10.4 本项目现有质量门的衔接

涉及后端：`mvn test`，必要时指定测试类和测试 profile。

涉及前端：`npm run type-check`、`npm run build-only`、相关 Playwright 测试。

涉及 Skill 或排版逻辑：Node test。

涉及跨前后端契约：接口/集成测试。

涉及 RAG：必须增加索引、过滤、幂等、删除、引用、权限和评测回归测试；不能只测“接口返回 200”。

## 11. 风险与控制

| 风险 | 表现 | 控制措施 |
|---|---|---|
| 文档过期 | AI 给出旧接口或旧配置 | Git commit、状态、复核日期、过期告警 |
| 权限越界 | 用户检索到其他项目/空间内容 | 后端硬过滤、集成测试、默认拒绝 |
| 提示注入 | 文档内容伪装成系统指令 | 数据/指令角色隔离、来源清洗、输出引用 |
| 语义误召回 | 搜到相似但错误模块 | 关键词召回、元数据过滤、重排 |
| 上下文过大 | 回答混乱、成本和延迟升高 | 章节级切分、topK、去重、上下文预算 |
| 文档泛滥 | 维护负担超过收益 | 只收录有 owner、有来源、有用途的文档 |
| 计划变成事实 | AI 把未执行方案当完成结果 | status 区分 proposed/verified，测试证据门禁 |
| 自动化过度 | 错误代码或迁移被直接执行 | 人工确认、分支隔离、测试先行、禁止生产写入 |
| 向量库故障 | 研发流程被 RAG 阻塞 | RAG 非阻塞降级、熔断、健康检查、离线索引 |

## 12. 对“个人能力吃力”的具体建议

不要一开始试图把整个项目解释完整。最小可行顺序是：

1. 先写一页项目地图：模块、入口、核心表、核心接口、测试入口。
2. 选一个高频模块，例如文章创作，完成一份业务文档和一份测试文档。
3. 选一个真实小需求，使用 grill 提问，产出计划，人工确认后实现。
4. 完成后让 AI 对照代码和测试更新文档，而不是让 AI 凭记忆写文档。
5. 把本次遗漏的问题加入下一轮 grill 问题集。

你不需要一次性成为产品经理、架构师、测试经理和知识工程师。AI 可以帮助整理、交叉引用和发现缺口，但“哪些规则是真的、哪些行为可接受、什么算完成”仍然需要你做最终判断。知识库的目标是降低每次重新解释项目的成本，而不是制造更多文档工作。

## 13. 最终建议

建议立项，但采用以下决策：

- **方向**：建设研发知识库，不建设泛化聊天机器人。
- **事实源**：Git 中的 Markdown/YAML、代码、SQL、测试和 ADR。
- **存储**：复用 Supabase pgvector 和现有 `RagService`，逐步增加关键词检索和结构化登记。
- **流程**：`grill me → write plan → 用户确认 → 小步实现 → 质量门 → 评审 → 文档沉淀`。
- **第一目标**：让 AI 能可靠回答“当前项目应该怎么改、为什么、影响什么、怎么测”，而不是让它代替开发者直接写完所有代码。
- **启动范围**：Phase 0 + Phase 1，先做文档治理和引用检索；通过固定问题集验证后再做代码图谱和自动化助手。

### 15.5 典型 `grill me` 任务

把以下任务直接交给 AI 时，要求它先提问，不得写代码：

> 在 `dev_rag` 分支为当前项目增加只读研发知识库问答。Git 是唯一事实源，后台和手工上传只作为待审核录入渠道。请先盘点现有 RAG、权限、文档和测试实现，再提出 P0 澄清问题。问题必须覆盖范围、角色、版本、文档状态、索引、检索、引用、异常、成本、验收和回滚。不要修改代码。

> 设计“手工上传研发文档”的实现计划。上传内容默认 `pending_review`，审核通过后才可检索；审核通过内容必须能回写 Git 并绑定 commit。请先说明当前代码可复用点、数据模型、接口、权限、状态流、失败恢复和测试矩阵，再生成文件级实施计划。不要实现。

> 修改 RAG 检索分块策略，使 Markdown 按标题层级切分、Java 按类/方法切分、SQL 按迁移切分。请先列出当前索引兼容性风险、需要重建的数据、评测集、回滚策略和预计影响文件。只有在计划确认后才进入代码阶段。

> 为文章创作模块补齐研发知识文档。请对照当前代码、接口和测试，分别产出业务文档、开发文档和测试文档草案；每个事实必须标注来源路径，每个无法确认的规则标为“待确认”，不要凭空补齐产品能力。

## 16. 已确认决策与后续问题

以下决策已由项目负责人确认，将作为后续 `dev_rag` 开发的约束：

1. 只服务当前项目，当前开发分支为 `dev_rag`。
2. Git 是统一事实源；保留管理后台和手工上传，但上传内容必须进入审核生命周期，审核通过后才可作为权威知识。
3. 后续开发再完善权限细节；Phase 1 仍必须在后端执行项目、用户和文档状态过滤。
4. 当前会话和后续实现均在 `dev_rag` 分支进行。
5. 接受关键词检索，与向量检索组成混合检索。
6. 第一阶段只读：允许检索、问答、引用和生成计划，不允许直接改 Git、审批文档、提交代码或执行生产操作。

开始 Phase 1 前仍需确认：

1. 当前项目的固定 `projectId` 和默认 owner/reviewer 是什么。
2. 手工上传审核通过后，采用人工复制到 Git、导出 PR，还是由后台生成可下载 Markdown。
3. 第一批优先验收的真实问题，从本节案例中选择至少 20 条。
